> ELK 전체 그림은 [ELK 스택 개요](https://rlckdwkd55.github.io/posts/elk-stack/)에,
> 가공 파이프라인은 [Logstash](https://rlckdwkd55.github.io/posts/logstash/)에 정리했다.
> 이 글은 파이프라인의 가장 앞단, 로그가 생기는 서버에서 로그를 안전하게 실어 나르는
> Filebeat를 다룬다.

로그 수집을 파이프라인 앞단에 붙일 때 서버마다 Logstash를 하나씩 띄우는 구성을 먼저
떠올리기 쉽다. 그러나 Logstash는 JVM 위에서 도는 무거운 프로세스라, 로그를 읽어 보내기만
하는 단순한 일에 서버 리소스를 과하게 쓴다. Elastic은 이 문제를 역할 분리로 푼다. 로그가
생기는 엣지(edge) 서버에는 최대한 가벼운 수집기를 두고, 무거운 가공은 중앙에서 처리한다.
이 경량 수집기 모음이 **Beats**이고, 그중 로그 파일을 담당하는 것이 **Filebeat**다.

---

## 엣지에 Filebeat를 두는 이유

Filebeat는 **Go로 작성된 단일 바이너리**다. JVM도 무거운 런타임도 필요 없이 메모리
수십 MB 수준으로 상주하며, 파일을 읽어 흘려보내는 데 특화돼 있다. 반면 Logstash는
grok·mutate 같은 본격적인 변환을 위한 도구라 그만큼 무겁다.

| 구분 | Filebeat | Logstash |
| --- | --- | --- |
| 런타임 | Go 단일 바이너리 | JVM |
| 리소스 | 메모리 수십 MB 수준 | 수백 MB~GB |
| 주 역할 | 수집·전송(가볍게) | 파싱·변환(무겁게) |
| 배치 위치 | 엣지(로그 서버마다) | 중앙 소수 |

핵심은 **수집은 가볍게 엣지에서, 가공은 무겁게 중앙에서**라는 분리다. 서버가 수십·수백
대로 늘어날수록 엣지에 무거운 프로세스를 곱하기로 얹지 않는 이 분리의 이득이 커진다.

## 최소 설정 — input과 output

Filebeat 설정은 **어디를 읽을지(input)**와 **어디로 보낼지(output)**로 나뉜다. 권장
입력 타입은 `filestream`이다(예전 `log` 타입은 deprecated).

```yaml
# filebeat.yml — 예시 (경로·호스트는 가공값)
filebeat.inputs:
  - type: filestream
    id: app-logs           # 입력마다 고유 id 필요
    enabled: true
    paths:
      - /var/log/app/*.log
    parsers:
      - multiline:         # 스택트레이스처럼 여러 줄인 로그를 한 이벤트로 묶기
          type: pattern
          pattern: '^\d{4}-\d{2}-\d{2}'
          negate: true
          match: after

output.logstash:                       # ES 직송이면 output.elasticsearch로 교체
  hosts: ["logstash.example.internal:5044"]
```

Elasticsearch 직송이라면 `output.elasticsearch`로 host를 지정하고, `pipeline`에 ingest
pipeline을 걸어 가벼운 파싱을 맡길 수 있다. output은 **둘 중 하나만** 활성화되며, 어느
쪽으로 보낼지는 뒤에서 따로 다룬다.

## 내부 동작 — input → harvester → registry → output

겉보기엔 "파일 읽어서 보낸다"지만, 안에서는 네 개의 톱니바퀴가 맞물려 돈다.

```text
[로그 파일]
   │
   ▼
input  ──(읽을 파일 탐색)──►  harvester (파일당 1개, 줄 단위로 읽음)
                                  │
                                  ▼
                            내부 큐(memory queue)
                                  │
                                  ▼
                               output ──► Logstash / Elasticsearch
                                  │
                                  ▼
                       registry에 offset 기록(전송 확인 후)
```

- **input** — 지정한 경로 패턴(`paths`)을 스캔해 읽을 파일을 찾고, 파일마다 harvester를 띄운다.
- **harvester(수확기)** — **파일 하나당 하나**가 붙어 파일을 열고 **한 줄씩** 읽는다. 파일을
  계속 열고 있어, 읽는 도중 파일이 회전(rotate)되거나 삭제돼도 열린 핸들로 남은 내용을
  마저 읽을 수 있다.
- **내부 큐** — harvester가 읽은 이벤트는 곧장 나가지 않고 libbeat의 메모리 큐에 잠깐
  쌓인다. 배치로 묶어 보내기 위한 완충 지대다.
- **output** — 큐의 이벤트를 Logstash나 Elasticsearch로 배치 전송한다.

### registry — "어디까지 읽었나"의 영속화

Filebeat의 신뢰성을 떠받치는 것이 **registry**다. 각 파일을 **어디까지 읽었는지(offset)**를
로컬 디스크(`data/registry`)에 계속 기록해 두므로, 프로세스가 재시작돼도 registry를 읽어
**마지막 offset 다음부터** 이어 읽는다. 파일을 처음부터 다시 읽어 로그가 통째로 중복되는
사고를 막는 장치다. 파일 식별은 이름이 아니라 inode 등의 식별자로 하기 때문에, 로그가
회전되며 이름이 바뀌어도 "같은 파일"로 추적한다.

---

## at-least-once — 중복은 허용하고 유실은 막는다

Filebeat의 전달 보장은 **최소 한 번(at-least-once)**이다. 이 설계는 registry와 함께 보면
분명해진다. Filebeat는 **output이 이벤트를 확실히 받았다는 확인(ACK)을 받은 뒤에야**
registry의 offset을 전진시킨다.

- 전송 → (확인 받기 전에 크래시) → **offset은 아직 그대로** → 재시작 시 그 지점부터 다시
  보냄 → 유실 없음, 대신 **일부 이벤트는 두 번 전송될 수 있음(중복)**.

즉 Filebeat는 **"유실보다 중복이 낫다"**는 쪽을 택한다. 로그·관측 데이터에서는 몇 건이
겹치는 것보다 몇 건이 사라지는 것이 훨씬 위험하기 때문이다. 중복은 하류에서 문서 ID를
고정하거나(멱등 색인) 중복 제거로 흡수할 수 있지만, 사라진 로그는 되살릴 방법이 없다.

---

## backpressure — 하류가 느려지면 스스로 늦춘다

Elasticsearch나 Logstash가 부하로 느려졌는데 Filebeat가 계속 밀어붙이면 하류가 더
무너진다. Filebeat는 이를 **backpressure(역압)**로 다룬다.

output이 느려지면 이벤트가 나가지 못해 **내부 큐가 차고**, 큐가 가득 차면 **harvester가
파일 읽기를 늦추거나 멈춘다**. 병목이 파일 읽기 단계까지 거슬러 올라와, Filebeat가 스스로
속도를 하류에 맞추는 구조다.

이것이 가능한 이유도 결국 registry다. 읽기를 멈춰도 offset이 남아 있으니, 하류가 회복되면
멈췄던 지점부터 다시 읽으면 된다. 데이터를 버리며 속도를 맞추는 게 아니라 **읽는 속도
자체를 늦춰** 유실 없이 버티는 방식이다.

## 모듈 — 정형 로그는 미리 만들어 둔 설정으로

Nginx, 시스템 로그(syslog), MySQL처럼 **포맷이 이미 알려진 로그**는 매번 input과 파싱을
직접 짤 필요가 없다. Filebeat는 이런 소스에 대해 **모듈(module)**을 제공하며, 모듈 하나에는
대개 기본 **입력 경로**, Elasticsearch **ingest pipeline**(로그를 필드로 파싱), Kibana
**대시보드**가 함께 들어 있다. 아래 한 줄로 nginx access/error 로그의 수집·파싱·시각화
기본이 갖춰진다.

```bash
filebeat modules enable nginx
```

## Logstash 직송이냐, Elasticsearch 직송이냐

output을 어디로 둘지는 **가공이 얼마나 필요한가**로 갈린다.

| 기준 | Filebeat → ES 직송 | Filebeat → Logstash → ES |
| --- | --- | --- |
| 가공 위치 | ES **ingest pipeline**(가벼운 파싱) | Logstash **filter**(grok 등 본격 가공) |
| 적합한 경우 | 모듈로 끝나는 정형 로그, 단순 수집 | 복잡한 파싱·필드 조작·다중 목적지 |
| 구성 복잡도 | 낮음(구성요소 하나 적음) | 높음(중앙에 Logstash 운용) |
| 버퍼링 | 제한적 | Logstash **persistent queue**로 완충 |

- **ES 직송** — 파싱이 가볍거나 모듈의 ingest pipeline으로 충분할 때. 구성요소가 하나 줄어
  운영이 단순하다.
- **Logstash 경유** — grok으로 비정형 로그를 본격적으로 쪼개거나, 여러 목적지로 분기하거나,
  큰 버퍼가 필요할 때. 자세한 내용은
  [Logstash 글](https://rlckdwkd55.github.io/posts/logstash/) 참고.

무엇을 택하든 **엣지의 Filebeat는 가볍게 유지한다**는 원칙은 그대로다.

---

## 요점

- Filebeat = Go로 만든 **경량 로그 수집기**(Beats 계열). 엣지에 무거운 Logstash 대신 얹어
  리소스를 아낀다.
- 내부는 **input → harvester(파일당 읽기) → 내부 큐 → output**, 그리고 **registry**가
  offset을 영속화해 **재시작 시 이어 읽기**를 보장한다.
- 전달은 **at-least-once**: ACK 후에만 offset을 전진시켜 유실을 막고 중복을 허용한다.
  로그에서는 "중복 < 유실"이라는 판단이다.
- 하류가 느려지면 **backpressure**로 읽기 속도를 스스로 늦춰 유실 없이 버틴다.
- 정형 로그는 **모듈**로, 가공이 가벼우면 **ES 직송**, 본격 가공이면 **Logstash 경유**.
