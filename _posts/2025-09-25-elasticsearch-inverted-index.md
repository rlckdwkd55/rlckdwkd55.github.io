관계형 데이터베이스에서 `LIKE '%검색어%'` 로 문자열을 찾으면 인덱스를 타지 못하는 **풀 스캔**이 된다. 앞이 와일드카드라 B-Tree 인덱스가 무력화되고, 모든 행의 문자열을 처음부터 끝까지 훑는다. 그래서 행 수에 비례해 느려진다. 검색 엔진은 이 문제를 조금 빠르게 만드는 게 아니라 **자료구조 자체를 다르게 잡아** 푼다. 그 핵심이 **역색인(inverted index)** 이다. Elasticsearch(이하 ES)는 Apache Lucene 위에 세워진 분산 검색 엔진이고, 색인·검색을 담당하는 실체는 전부 Lucene의 역색인이다. 따라서 "ES가 왜 빠른가"라는 질문의 답은 "Lucene이 데이터를 어떻게 저장하는가"로 내려간다.

## 정방향 색인과 역색인

두 방향을 먼저 구분한다.

- **정방향 색인(forward index)**: "문서 → 그 문서에 들어 있는 단어들". 문서를 열어야 안에 무슨 단어가 있는지 알 수 있다. RDB의 한 행을 읽는 것과 같다.
- **역색인(inverted index)**: 방향을 뒤집어 **"단어 → 그 단어가 등장한 문서 목록"** 을 저장한다.

```text
원본 문서
  문서1: "사과 바나나"
  문서2: "사과 딸기"

역색인
  바나나 → [문서1]
  딸기   → [문서2]
  사과   → [문서1, 문서2]
```

"사과"를 검색하면 전체 문서를 훑지 않는다. 역색인에서 "사과" 항목 하나만 조회해 곧바로 `[문서1, 문서2]` 를 얻는다. 데이터가 아무리 많아도 사전에서 단어를 찾듯 조회한다. 용어를 정리하면 다음과 같다.

- **텀(term)**: 색인의 최소 단위가 되는 단어. 원문 단어와 반드시 같지는 않다(뒤에서 설명할 분석 과정을 거친다).
- **텀 사전(term dictionary)**: 정렬된 텀들의 집합. "어떤 텀이 존재하는가"를 답한다.
- **포스팅 리스트(posting list)**: 하나의 텀이 등장한 문서 ID 목록. "그 텀이 어디에 있는가"를 답한다.

즉 역색인은 **텀 사전 + 포스팅 리스트** 두 축으로 이뤄진다. 검색은 (1) 텀 사전에서 질의 텀을 찾고 (2) 그 텀의 포스팅 리스트를 꺼내오는 두 단계다.

## 포스팅 리스트에 담기는 정보

"포스팅 리스트 = 문서 ID 목록"은 흔한 오해다. 실제 Lucene의 포스팅에는 용도에 따라 더 많은 정보가 함께 저장된다.

| 저장 정보 | 무엇인가 | 어디에 쓰이나 |
|---|---|---|
| 문서 ID (doc ID) | 이 텀이 나온 문서 | 매칭 여부 판정 |
| 텀 빈도 (term frequency) | 그 문서에서 몇 번 나왔나 | 관련도 점수(TF) |
| 위치 (positions) | 문서 내 몇 번째 토큰인가 | 구(phrase)·근접 검색 |
| 오프셋 (offsets) | 원문에서의 문자 시작·끝 위치 | 하이라이팅 |

이 정보 덕분에 `"사과 주스"` 를 따옴표로 묶은 **구 검색**이 가능하다. "사과"와 "주스"가 같은 문서에 있는 것만으로는 부족하고, "사과" 바로 다음 위치에 "주스"가 와야 한다는 조건을 positions로 판정하기 때문이다. 부가 정보를 얼마나 저장할지는 매핑의 `index_options`(`docs` / `freqs` / `positions` / `offsets`)로 조절한다. 정확 일치만 필요하면 빈도·위치를 끄고 색인 크기를 줄일 수 있다.

## 분석 — 텍스트가 텀이 되기까지

원문 텍스트가 곧바로 역색인에 들어가는 게 아니다. **분석기(Analyzer)** 를 거쳐 텀으로 쪼개진다. 분석기는 세 단계의 파이프라인이다.

1. **Character Filter** — 토큰화 이전 원문 전처리. HTML 태그 제거(`html_strip`), 특정 문자 치환 등. 예: `<p>C++</p>` → `C++`
2. **Tokenizer** — 텍스트를 토큰으로 분리. **정확히 하나만** 놓인다. 공백 기준, 문자 기준, 형태소 기준 등.
3. **Token Filter** — 토큰 후처리. 소문자화(`lowercase`), 불용어 제거(`stop`), 동의어 확장(`synonym`), 어간 추출(`stemming`) 등. **0개 이상** 체인으로 붙는다.

`_analyze` API로 실제로 어떤 텀이 나오는지 직접 확인할 수 있다.

```text
POST /_analyze
{
  "analyzer": "standard",
  "text": "The Quick Brown-Fox"
}
```

```text
// 결과 (요약): standard analyzer는 소문자화 + 문장부호 분리
{ "tokens": [
  { "token": "the",   "position": 0 },
  { "token": "quick", "position": 1 },
  { "token": "brown", "position": 2 },
  { "token": "fox",   "position": 3 }
]}
```

`Brown-Fox` 가 하이픈에서 갈라지고 전부 소문자가 됐다. 이렇게 나온 텀들이 역색인에 들어간다. 그래서 "brown"으로 검색하면 걸리지만, 분석 없이 원문 그대로 저장했다면 "Brown"이나 "Brown-Fox"만 걸렸을 것이다.

여기서 가장 중요한 규칙이 나온다. **색인 시점과 검색 시점에 서로 짝이 맞는 분석을 적용해야 한다.** 색인 때 "Running"을 `run` 으로 저장해 놓고 검색어 "Running"을 분석 없이 그대로 찾으면 텀 사전에 `Running` 이 없어 매칭되지 않는다. 검색어도 같은(혹은 대응되는) 분석기를 통과해 `run` 이 되어야 비로소 만난다. "분명 있는데 안 잡히는" 검색 버그의 대부분이 여기서 나온다. 한국어는 조사·어미가 어간에 달라붙는 교착어라 이 단계가 더 중요한데, 공백 토크나이저로는 "학교"가 "학교에서"를 못 잡는다. 형태소 분석기는 [Nori 분석기 글](https://rlckdwkd55.github.io/posts/nori-analyzer/)에서 따로 다뤘다.

## ES의 데이터 모델

역색인이라는 엔진 위에 ES가 얹은 개념들은 다음과 같다.

- **문서(Document)** — 검색 대상 하나. JSON 형태이며, 색인의 최소 단위다.
- **필드(Field)** — 문서의 속성. **필드 타입에 따라 분석 여부가 갈린다.**
  - `text`: 분석기를 거쳐 텀으로 쪼개진다. 전문 검색(full-text search)용.
  - `keyword`: **분석하지 않고** 값 전체를 하나의 텀으로 저장. 정확 일치·정렬·집계용.
- **인덱스(Index)** — 문서의 모음. RDB의 테이블에 비유하지만 스키마 정의는 **매핑(mapping)** 으로 한다.
- **샤드(Shard)** — 인덱스를 물리적으로 나눈 조각. 분산·확장의 단위이며, **하나의 샤드가 곧 하나의 Lucene 인덱스**다. 문서는 어느 샤드로 라우팅되어 그 샤드의 역색인에 들어간다.

`text` 와 `keyword` 를 혼동하면 검색이 어긋난다. 한 필드에 둘 다 필요할 때가 많아, 실무에서는 `text` 로 두되 하위 필드로 `keyword` 를 같이 매핑하는 **멀티 필드**를 흔히 쓴다.

```text
PUT /articles
{
  "mappings": {
    "properties": {
      "title": {
        "type": "text",              // 본문 검색용: 분석되어 텀으로 쪼개짐
        "fields": {
          "raw": { "type": "keyword" } // title.raw: 정렬·집계·정확일치용
        }
      },
      "tags":       { "type": "keyword" },  // 태그는 통째로 정확히 매칭
      "created_at": { "type": "date" }
    }
  }
}
```

이러면 `title` 로는 "스프링 부트 튜토리얼"을 단어 단위로 검색하고, `title.raw` 로는 제목 전체를 정렬 키나 집계 버킷으로 쓸 수 있다. 이메일·태그·상태 코드처럼 통째로 정확히 맞춰야 하는 값은 `keyword`, 문장·본문처럼 부분·의미 검색이 필요한 값은 `text` 로 잡는다.

## 세그먼트, 불변성, near-real-time

여기까지가 "역색인이 무엇인가"라면, 이제 "그 역색인이 디스크에 어떻게 앉고 갱신되는가"다. 운영에서 겪는 성능·지연 이슈의 상당수가 이 지점에서 나온다.

Lucene 인덱스(=샤드)는 여러 개의 **세그먼트(segment)** 로 이뤄진다. 세그먼트는 그 자체로 완결된 작은 역색인이다. 핵심 성질은 하나다. **세그먼트는 한 번 쓰이면 불변(immutable)이다.**

불변이면 락 없이 여러 스레드가 동시에 읽을 수 있고, OS 파일 시스템 캐시에 통째로 올려 두고 재사용할 수 있으며, 압축·구조를 읽기에 최적으로 고정할 수 있다. 대신 문서를 새로 넣거나 지워도 기존 세그먼트를 못 고친다는 대가가 따른다.

- **추가**: 새 문서는 기존 세그먼트를 건드리지 않고 **새 세그먼트**로 쌓인다.
- **삭제**: 실제로 지우지 않는다. `.del` 성격의 정보로 "이 문서는 지워졌다"고 **표시(tombstone)** 만 해 둔다. 검색 결과에서 걸러질 뿐 물리적으로는 남아 있다.
- **수정**: in-place update는 없다. 내부적으로 **기존 문서를 삭제 표시하고 새 문서를 추가**한다.

문서를 색인해도 곧바로 검색되지는 않는다. 새 문서는 먼저 인메모리 버퍼에 있다가, **refresh** 가 일어나야 새 세그먼트로 만들어져 검색 대상이 된다. 기본 주기가 1초라 ES를 "거의 실시간(near-real-time)"이라 부른다. 완전한 실시간이 아니라 **최대 refresh 주기만큼 지연**될 수 있다는 뜻이다. 색인 직후 조회했는데 안 나온다면 대개 이 때문이다.

여기서 refresh와 flush를 구분한다.

| 동작 | 하는 일 | 목적 |
|---|---|---|
| refresh | 버퍼의 문서를 새 세그먼트로 만들어 **검색 가능**하게 함 | 검색 가시성 (기본 1초) |
| flush | 세그먼트를 디스크에 **fsync**하고 translog를 비움 | 영속성(durability) |

refresh만으로는 아직 디스크에 안전하게 확정된 게 아니다. 그 사이 장애가 나도 데이터를 잃지 않도록 ES는 **translog(트랜잭션 로그)** 에 먼저 기록해 두고, flush 시점에 세그먼트를 확정하며 translog를 정리한다.

## 세그먼트 병합(merge)

refresh가 1초마다 일어나면 작은 세그먼트가 계속 늘어난다. 검색은 **모든 세그먼트를 조회한 뒤 결과를 합치므로**, 세그먼트가 수백 개면 열어 볼 파일이 많아져 느려진다. 게다가 삭제 표시된 문서가 세그먼트에 계속 남는다.

그래서 Lucene은 백그라운드에서 작은 세그먼트들을 **더 큰 세그먼트 하나로 병합(merge)** 한다. 병합 과정에서 삭제 표시된 문서가 비로소 실제로 빠지고, 파일 개수가 줄어 검색이 가벼워진다. 병합은 이득이 크지만 디스크 I/O와 CPU를 쓰는 무거운 작업이라, 대량 색인 중에는 merge가 병목이 되기도 한다. "역색인은 불변이다"라는 결정 하나가 refresh·flush·merge·translog라는 운영 메커니즘 전체로 번지는 셈이다.

## 텀 사전과 포스팅의 내부 구조

"사전에서 단어 찾듯 빠르다"고 했는데, 그 사전 자체의 구조도 짚어 둘 만하다. 텀이 수백만 개일 때 단순 정렬 배열을 이진 탐색하는 것도 방법이지만, Lucene은 텀 사전의 인덱스를 **FST(Finite State Transducer)** 로 만든다. 공통 접두사·접미사를 공유하는 오토마톤이라 메모리를 아주 적게 쓰면서 "이 텀이 있나, 있다면 포스팅이 어디 있나"를 빠르게 답한다. 이 구조 덕분에 접두사 검색(`auto*`)이나 오타 보정 같은 기능도 자연스럽게 얹힌다.

포스팅 리스트도 단순 배열이 아니다. 문서 ID를 차이값으로 압축(delta 인코딩)해 저장하고, 긴 리스트를 건너뛰며 탐색하도록 **스킵 리스트(skip list)** 를 둔다. 여러 텀의 포스팅을 교집합(AND 질의)할 때 이 스킵 구조가 결정적으로 빠르다.

## 텀 빈도가 점수가 되는 지점

역색인과 검색 점수가 어떻게 이어지는지 본다. 앞서 포스팅 리스트에 **텀 빈도(TF)** 가 함께 저장된다고 했고, 포스팅 리스트의 **길이** 자체가 곧 "그 텀을 가진 문서 수", 즉 **문서 빈도(DF)** 다. 여기서 검색의 관점이 바뀐다.

RDB의 `WHERE` 는 참/거짓만 답한다. 하지만 검색은 "맞다/아니다"가 아니라 **"얼마나 관련 있나"** 의 문제다. ES의 기본 랭킹 알고리즘 **BM25** 는 역색인에 이미 들어 있는 통계를 그대로 재료로 쓴다.

- **TF**(term frequency): 질의 텀이 그 문서에 자주 나올수록 관련도가 높다. 단, 무한정 높아지지 않고 **포화(saturation)** 한다 — 100번 나온다고 10번 나온 문서의 10배가 아니다.
- **IDF**(inverse document frequency): 전체 문서에서 **희귀한 텀일수록** 변별력이 크다. "the", "은/는" 같이 아무 데나 나오는 텀은 점수 기여가 작다. IDF는 앞서 말한 DF에서 바로 계산된다.
- **필드 길이 정규화**: 짧은 필드에서 매칭된 텀을 긴 필드에서 매칭된 것보다 더 관련 있다고 본다.

즉 역색인은 단순히 "어디 있나"를 저장하는 자료구조가 아니라 **랭킹에 필요한 통계를 이미 품고 있는** 구조다. 그래서 매칭과 점수 계산이 별도 데이터 없이 한 번에 이뤄진다. BM25의 수식과 파라미터(`k1`, `b`)는 [BM25 글](https://rlckdwkd55.github.io/posts/bm25/)에서 따로 파고들었다.

역색인은 `LIKE '%...%'` 풀 스캔을 자료구조부터 다르게 뒤집은 구조로, 텀 사전과 포스팅 리스트라는 두 축 위에서 매칭·구 검색·하이라이팅·랭킹을 한꺼번에 지탱한다. 그 위에 분석기가 텀을 만들고, 세그먼트 불변성이 refresh·flush·merge라는 운영 메커니즘을 낳으며, 포스팅에 담긴 TF·DF 통계가 그대로 BM25 점수로 이어진다.
