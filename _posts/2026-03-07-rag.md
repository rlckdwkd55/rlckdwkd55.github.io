## 들어가며

LLM을 서비스에 붙이면 곧 한계가 드러난다. 모델은 그럴듯하게 답하지만, 사내 문서를
모르고, 최신 정보를 모르며, 모르는 것을 모른다고 하지 않는다.
**RAG(Retrieval-Augmented Generation)** 는 이 문제를 "모델을 다시 학습시키는" 대신
"답하기 전에 관련 문서를 찾아 근거로 넣어 주는" 방식으로 푼다. 2020년 Lewis 등의
논문에서 제안된 뒤 LLM 애플리케이션의 사실상 표준 아키텍처가 되었다.

---

## 왜 RAG인가 — LLM의 구조적 한계

LLM의 지식은 학습 시점에 **가중치(parameter) 안에 얼어붙은** 형태로 들어 있다.
여기서 세 가지 한계가 나온다.

1. **지식 컷오프(cutoff)** — 학습 이후의 사건·자료는 알 수 없다.
2. **비공개 도메인 부재** — 사내 문서·매뉴얼처럼 학습에 없던 지식은 존재하지 않는다.
3. **할루시네이션** — 파라미터에 답이 없을 때도 통계적으로 그럴듯한 문장을 생성한다.

파인튜닝으로 지식을 넣을 수도 있지만, 비용이 크고 자주 갱신하기 어려우며 출처를
제시하지 못한다. RAG는 지식을 **모델 밖(외부 저장소)** 에 두고 필요할 때 꺼내 쓰므로,
문서만 갱신하면 지식이 최신화되고 답변에 출처를 붙일 수 있다. "지식과 추론의 분리"가
RAG의 본질이다.

---

## 전체 그림

RAG는 미리 준비하는 **색인(Indexing)** 과, 요청 때마다 도는 **질의(Query)** 로 나뉜다.

```text
[색인]  문서 → 분할(Chunk) → 임베딩 → 벡터 DB 저장
[질의]  질문 → 임베딩 → 검색(top-k) → (리랭킹) → 프롬프트 구성 → LLM 생성 → 답변(+출처)
```

## 1. 색인 파이프라인

### 문서 분할(Chunking)

LLM 컨텍스트와 검색 정밀도 때문에 문서를 청크로 쪼갠다. 전략에 따라 검색 품질이 갈린다.

- **고정 크기** — N 토큰씩 자르기. 단순하지만 문장·문단 중간이 잘린다.
- **재귀 분할** — 문단→문장→토큰 순으로 자연 경계를 우선 사용(가장 흔함).
- **의미 기반(semantic)** — 인접 문장 임베딩 유사도가 떨어지는 지점에서 분할.
- **오버랩(overlap)** — 청크 경계에서 문맥이 끊기지 않도록 앞뒤를 일부 겹친다.

청크가 너무 크면 검색에 노이즈가 섞이고, 너무 작으면 문맥이 잘려 답이 부실해진다.
"검색 단위 = 답변 근거 단위"라는 감각으로 도메인에 맞춰 튜닝한다.

### 임베딩(Embedding)

각 청크를 의미를 담은 고차원 벡터로 변환한다. 의미가 비슷한 텍스트는 벡터 공간에서
가깝게 위치한다. 한국어·다국어에는 `bge-m3` 같은 모델이, 영어권에는 OpenAI
`text-embedding-3` 등이 쓰인다. **질문과 문서를 반드시 같은 임베딩 모델로** 변환해야
같은 좌표계에서 비교가 된다(모델이 다르면 차원·좌표계가 어긋난다).

### 저장(Indexing)과 ANN

수백만 개 벡터에서 매번 전수 비교(brute force)를 하면 느리다. 그래서 벡터 DB는
**근사 최근접 이웃(ANN, Approximate Nearest Neighbor)** 인덱스를 쓴다. 대표적으로
**HNSW(Hierarchical Navigable Small World)** 는 그래프를 계층적으로 탐색해 정확도를
거의 유지하면서 속도를 크게 끌어올린다. 정확도(recall)와 속도는 트레이드오프이며
`ef`, `M` 같은 파라미터로 조절한다.

## 2. 검색(Retrieval)

### 유사도 측정

밀집 벡터 검색은 보통 **코사인 유사도**(두 벡터가 이루는 각도)로 가까움을 잰다.
크기(norm)가 아니라 방향을 보기 때문에 문서 길이에 덜 민감하다.

### 세 가지 검색 방식

- **희소(Sparse) 검색 — BM25**: 단어 빈도(TF)와 희귀도(IDF)로 점수를 매기는 전통적
  키워드 검색. "정확히 이 단어"에 강하고, 고유명사·코드·숫자에 유리하다. 반대로
  동의어·의역은 못 잡는다.
- **밀집(Dense) 검색 — 임베딩**: 의미 기반. 표현이 달라도 뜻이 가까우면 찾는다.
  대신 정확한 키워드 매칭은 약할 수 있다.
- **하이브리드 검색**: 둘을 함께 돌려 결과를 합친다. 키워드의 정밀함과 의미 검색의
  포용성을 모두 취한다.

### 결과 합치기 — RRF

서로 점수 체계가 다른 두 검색 결과를 어떻게 합칠까? **RRF(Reciprocal Rank Fusion)** 는
점수의 절대값 대신 **순위(rank)** 만 사용한다.

```text
RRF_score(d) = Σ  1 / (k + rank_i(d))      (i: 각 검색기, k ≈ 60)
```

각 검색기에서의 등수를 역수로 더하는 방식이라, 스케일이 다른 점수를 정규화하지 않고도
안정적으로 융합된다. 여러 검색기 상위에 공통으로 오른 문서가 자연히 위로 올라온다.
(반대로 "코사인 0.9 이상"처럼 **절대 임계값**이 필요할 땐 RRF 점수가 부적합해, 밀집
전용 검색을 따로 쓰기도 한다.)

## 3. 리랭킹(Reranking)

1차 검색은 속도를 위해 **Bi-Encoder**(질문·문서를 각각 임베딩해 비교)를 쓴다. 빠르지만
질문과 문서의 상호작용을 못 본다. 그래서 상위 k개만 뽑아 **Cross-Encoder**(질문+문서를
한 번에 넣어 관련도를 직접 채점)로 다시 정렬한다.

| | Bi-Encoder | Cross-Encoder |
|---|---|---|
| 방식 | 각각 임베딩 후 유사도 | 질문+문서 함께 입력해 점수 |
| 속도 | 빠름(사전 계산 가능) | 느림(쌍마다 추론) |
| 정확도 | 보통 | 높음 |
| 용도 | 1차 대량 검색 | 상위 소수 재정렬 |

"Bi-Encoder로 넓게 뽑고 → Cross-Encoder로 좁혀 정렬"하는 2단계가 정확도와 비용의
현실적 타협점이다.

---

## 4. 생성(Generation)과 신뢰성 장치

검색·리랭킹으로 고른 청크를 프롬프트에 넣어 LLM이 그 근거 위에서 답한다. 여기서도
할루시네이션을 더 눌러 주는 장치가 있다.

- **관련성 평가(Document Grading)** — 검색된 문서가 실제로 질문과 관련 있는지 먼저
  걸러, 엉뚱한 근거로 답하지 않게 한다.
- **질의 재작성(Query Rewrite)** — 검색이 빈약하면 질문을 다시 써서 재검색한다.
- **답변 검증** — 생성된 답변이 근거를 벗어나지 않았는지(용어·사실) 확인하고, 벗어나면
  재생성한다.

---

## 심화 기법

- **Multi-query / HyDE** — 질문을 여러 형태로 확장하거나, "가상의 이상적인 답변"을 먼저
  생성해 그 임베딩으로 검색해 회수율을 높인다.
- **Self-RAG / CRAG** — 모델이 검색 필요 여부·검색 품질을 스스로 판단해 흐름을 바꾼다.
- **Contextual/Parent-Child 청킹** — 검색은 작은 청크로, 생성은 그 부모 문단으로 넘겨
  정밀도와 문맥을 동시에 챙긴다.

---

## 평가

RAG는 "검색"과 "생성"을 나눠서 평가해야 원인을 찾는다.

- **검색 품질**: Recall@k, MRR, nDCG — 정답 근거가 상위에 잘 올라오는가.
- **생성 품질**: 충실성(faithfulness, 근거를 벗어나지 않았는가), 답변 관련성, 정확성.
  최근엔 **LLM-as-a-Judge**(다른 LLM이 채점)나 RAGAS 같은 프레임워크를 많이 쓴다.

---

## 한계와 트레이드오프

- **검색이 곧 상한선** — 근거를 못 찾으면 생성도 실패한다(garbage in, garbage out).
- **지연·비용 증가** — 임베딩·검색·리랭킹·LLM까지 단계가 늘어난다.
- **청크·임베딩 민감성** — 튜닝 포인트가 많고, 잘못 나누면 성능이 급락한다.
- **컨텍스트 한계 / lost-in-the-middle** — 너무 많이 넣으면 중간 정보를 놓친다. 적게,
  정확하게 넣는 게 낫다.
- 지식이 자주 안 바뀌고 소규모라면, RAG보다 프롬프트에 직접 넣거나 파인튜닝이 나을 수도.

---

RAG는 지식(외부 검색)과 추론(LLM)을 분리해 최신성·도메인·할루시네이션 문제를 완화하는
구조다. 분할 → 임베딩 → (ANN) 저장 → 검색(희소/밀집/하이브리드+RRF) → 리랭킹 → 생성으로
이어지는 파이프라인에서 품질의 병목은 언제나 검색이며, 청킹·임베딩·하이브리드·리랭킹·검증이
답변의 상한을 결정한다.
