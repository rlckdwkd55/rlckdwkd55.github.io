인증(authentication)이 "요청을 보낸 주체가 누구인가"를 확인하는 문제라면, 인가
(authorization)는 "그 주체가 이 동작을 해도 되는가"를 판정하는 문제다. 인증 쪽은
[JWT 정리](https://rlckdwkd55.github.io/posts/jwt/)에서 다뤘고, 이 글은 인증이
끝난 다음 단계인 인가만 다룬다.

인가를 가장 단순하게 구현하면 `if user.id == owner_id` 같은 조건을 필요한 곳마다
직접 넣게 된다. 기능이 늘면 이 조건이 코드 곳곳에 흩어지고, "누가 무엇을 할 수 있는가"를
한곳에서 볼 수 없게 된다. **RBAC(Role-Based Access Control, 역할 기반 접근 제어)**
는 권한을 사용자에게 직접 부여하지 않고 **역할(role)** 이라는 중간 계층으로 매개해 이
문제를 구조화한다.

## 왜 사용자에 권한을 직접 붙이지 않나

가장 단순한 방식은 사용자마다 권한 목록을 직접 들고 있는 것이다.
`사용자 A = [문서 조회, 문서 생성, 스케줄러 실행]` 같은 식이다. 사람이 몇 명일 때는
문제가 없지만 **규모**가 커지면 무너진다.

편집자 역할을 하는 사람이 100명이라고 하자. 직접 부여 방식에서는 편집자 권한 정책이
바뀔 때마다 **100명분을 전부** 고쳐야 한다. 한 명이라도 빠뜨리면 그대로 권한 사각지대가
된다. 관리 비용이 사용자 수에 비례해 늘어난다.

RBAC는 여기에 **역할**이라는 한 단계를 끼워 넣는다.

```text
사용자(User) ──▶ 역할(Role) ──▶ 권한(Permission)
  사용자 A       편집자        문서 C/R/U, 댓글 C/R/U/D
  사용자 B       편집자
  사용자 C       뷰어          문서 R, 댓글 R
```

- 권한은 **역할에 모아** 정의하고, 사용자에게는 **역할만** 붙인다.
- "편집자" 권한을 한 번 고치면 편집자 100명에게 **동시에** 반영된다.
- 새 사용자가 들어와도 역할 하나만 배정하면 된다. 권한을 일일이 나열할 필요가 없다.

관리 대상이 `사용자 × 권한`(곱)에서 `역할 × 권한 + 사용자 × 역할`(합)으로 바뀐다.
사용자가 많고 권한 종류가 많을수록 이 차이는 벌어진다. RBAC가 규모에서 유리한 이유가
이 구조에 있다.

## 3요소와 역할 계층

RBAC는 세 엔티티와 그 사이의 두 매핑으로 이뤄진다.

- **User** — 실제 사람 또는 서비스 계정.
- **Role** — 업무 성격으로 묶은 권한 꾸러미. "편집자", "감사자", "결제 담당" 등.
- **Permission** — "무엇에 대해 무엇을 할 수 있는가"의 최소 단위. `문서:삭제` 같은 것.

매핑은 둘이다. `User ↔ Role`(다대다: 한 사람이 여러 역할을 겸할 수 있다)과
`Role ↔ Permission`(다대다: 한 역할이 여러 권한을, 한 권한이 여러 역할에 속한다).

역할이 늘면 **역할 계층(role hierarchy)** 이라는 개념이 등장한다. 상위 역할이 하위
역할의 권한을 **상속**하는 구조다.

```text
관리자(Admin)                        ← 편집자 권한 전부 + 관리자 고유 권한
   └─ 편집자(Editor)                 ← 뷰어 권한 전부 + 편집자 고유 권한
        └─ 뷰어(Viewer)              ← 기본 열람 권한
```

이렇게 두면 "편집자는 뷰어가 할 수 있는 건 다 할 수 있다"를 권한 복사 없이 표현할 수
있다. 다만 계층이 깊어지면 "이 역할이 결국 무슨 권한을 갖는지" 추적이 어려워진다.
계층은 **2~3단 안쪽**으로 얕게 유지하고, 애매하면 평평하게(flat) 가는 편이 디버깅에
유리하다.

## 권한 매트릭스 — 리소스 × 액션

<!-- 이미지: 구글 검색 "rbac role permission matrix" · 저장 /assets/img/posts/security/rbac/permission-matrix.png -->

권한을 머릿속에서만 다루면 금세 헷갈린다. 실무에서 자주 쓰는 정리 방법이 **리소스(행) ×
액션(열)** 표, 즉 권한 매트릭스다. 아래는 가공한 예시다.

| 리소스 \ 액션 | 조회(R) | 생성(C) | 수정(U) | 삭제(D) | 실행(E) |
|---|:---:|:---:|:---:|:---:|:---:|
| 문서 관리 | O | O | O | X | — |
| 사용자 관리 | O | O | O | O | — |
| 스케줄러 | O | X | X | X | O |
| 외부 DB 연결 | O | O | O | X | O |

이 표가 곧 한 역할이 갖는 권한의 전체상이다. 위 매트릭스는 "운영자" 역할의 예로 볼 수
있다. 한 칸(리소스 × 액션)이 permission 하나에 대응한다.

여기서 놓치기 쉬운 축이 **실행(Execute)** 이다. CRUD 4개면 충분해 보이지만,
"스케줄러 즉시 실행", "외부 DB 연결 테스트", "문서 재동기화"처럼 **데이터를 바꾸는 게
아니라 어떤 동작을 트리거하는** 액션은 CRUD 어디에도 깔끔히 들어가지 않는다. 억지로
`update`에 욱여넣으면 의미가 흐려지고, 결국 권한 검사 없이 열려 버리기 쉽다. CRUD에
**실행(E)** 을 더한 5축 모델로 잡으면 비-CRUD 액션에도 자연스럽게 권한 게이트를 걸 수
있다.

## RBAC vs ABAC — 언제 무엇을

RBAC만 정답은 아니다. 자주 비교되는 것이 **ABAC(Attribute-Based Access Control,
속성 기반 접근 제어)** 다. ABAC는 역할 대신 **속성**과 **규칙**으로 판정한다. "부서가
같고, 근무 시간대이며, 문서 등급이 사용자 등급 이하이면 허용" 같은 식이다.

| 기준 | RBAC | ABAC |
|---|---|---|
| 판정 근거 | 역할(role) | 속성(사용자·리소스·환경) + 규칙 |
| 표현력 | 정적·거친 단위 | 동적·세밀한 조건 |
| 이해 난이도 | 낮음(표로 보임) | 높음(규칙 조합) |
| 관리 비용 | 역할 수가 적으면 저렴 | 규칙이 늘면 복잡 |
| 대표 함정 | 역할 폭발(role explosion) | 규칙 충돌·디버깅 난이도 |

대부분의 사내·업무 시스템은 RBAC로 충분하다. "누가 무슨 역할이고 그 역할이 무엇을
하는지"가 표 하나로 보이는 명료함이 크다. 반대로 "본인이 작성한 문서만", "같은 팀
데이터만", "특정 시간대에만" 같은 **문맥 의존 조건**이 핵심이면 ABAC가 맞다. 현실적인
절충은 RBAC를 뼈대로 두고 소유권 검사(`owner_id == user_id`) 같은 몇몇 조건만 ABAC
스타일로 얹는 혼합형이다. 역할이 조건마다 쪼개지며 수십 개로 늘어나는 **역할 폭발**이
보이면, 그 축은 ABAC로 빼야 한다는 신호다.

## 구현 관점 — 어디서 검사하나

개념이 정리되면 남는 건 "실제 요청에서 언제, 어디서 판정하느냐"다. 세 지점이 있다.

**1) 토큰에 역할/권한을 실어 전달.** 로그인 시 발급하는 JWT payload에 역할이나 권한
요약을 담아 두면 매 요청마다 DB를 조회하지 않아도 되는 경우가 있다.

```json
{
  "sub": "user-1024",
  "roles": ["editor"],
  "is_admin": false
}
```

단, 토큰은 **발급 시점의 스냅샷**이다. 권한을 회수해도 이미 발급된 토큰에는 옛 권한이
남아 있으므로, 민감한 권한은 토큰만 믿지 말고 서버에서 다시 조회하는 편이 안전하다.

**2) 서버측 게이트(미들웨어/의존성/데코레이터).** 핵심은 **엔드포인트 진입 시점에**
"이 사용자 역할이 이 리소스에 이 액션을 할 수 있나"를 공통 함수로 검사하는 것이다.
Spring Security의 메서드 시큐리티, FastAPI의 의존성 등 프레임워크마다 이름은 다르지만
발상은 같다. Spring 진영의 필터 기반 인가 흐름은
[Spring Security 정리](https://rlckdwkd55.github.io/posts/spring-security/)에서 다뤘다.

```python
# 개념 예시(가공): 라우트에 권한 게이트를 선언적으로 건다
@router.delete(
    "/documents/{doc_id}",
    dependencies=[Depends(require_can("document", "delete"))],
)
async def delete_document(doc_id: int): ...
```

`require_can`은 요청자의 역할 → 권한을 조회해 허용 여부만 판정하고, 안 되면 403을
던진다. 이 게이트를 FastAPI 의존성으로 실제 구현하고 실행(Execute) 권한까지 붙인 과정은
[RBAC 권한 게이트 구현](https://rlckdwkd55.github.io/posts/rbac-permission-gate/)에서
따로 다룬다.

**3) 프런트 숨김은 검사가 아니다.** 권한 없는 메뉴를 사이드바에서 숨기는 것은 어디까지나
**UX**다. 버튼이 안 보여도 누군가 API를 직접 호출하면 그만이다. 따라서 원칙은 하나다.
**프런트에서 숨기더라도 서버에서 반드시 다시 검증한다.** 화면 제어와 실제 권한 판정은
같은 권한 모델을 참조하되, **믿을 수 있는 판정은 서버 쪽 하나뿐**이다.

## 최소 권한과 권한 상승

RBAC를 잘 세팅해도 운영이 흐트러지면 무너진다. 운영 원칙은 다음과 같다.

- **기본은 거부(deny by default).** 명시적으로 허용한 것만 통과시킨다. 새 리소스가
  생기면 아무 역할에도 권한이 없는 상태가 기본값이어야 한다.
- **최소 권한(least privilege).** 역할에는 그 업무에 꼭 필요한 권한만 준다. "혹시
  몰라서" 넉넉히 준 권한이 사고의 씨앗이 된다.
- **광역 우회 플래그를 아낀다.** `is_admin` 하나로 모든 검사를 건너뛰게 만들면 편하지만,
  그것이 곧 가장 큰 사각지대다. 관리자도 가능하면 역할 권한으로 판정하고, 우회는 최소한으로만.
- **권한 상승(privilege escalation) 경로를 의심한다.** "역할을 바꾸는 API" 자체에
  권한 검사가 없으면 일반 사용자가 스스로를 관리자로 승격시킬 수 있다. 권한을 다루는
  기능일수록 가장 강하게 잠가야 한다.

RBAC는 권한을 어떻게 **구조화**하느냐의 답이고, 최소 권한·기본 거부는 그 구조를 어떻게
**운영**하느냐의 답이다. 정리하면 이렇다. 권한을 역할로 매개하면 관리 대상이 곱에서 합으로
줄고, 정책 변경이 역할 하나 수정으로 끝난다. 뼈대는 User–Role–Permission 3요소와 두
매핑, 그리고 상속을 표현하는 역할 계층이며 계층은 얕게 유지한다. 권한은 리소스 × 액션
(CRUD + 실행E) 매트릭스로 보면 전체상이 한눈에 잡히고, 실행(E) 축이 비-CRUD 동작의
권한 구멍을 막는다. 문맥 의존 조건이 핵심이면 ABAC, 그 외 대부분은 RBAC로 충분하다.
무엇보다 서버측 재검증이 유일한 진짜 판정이며, 토큰은 스냅샷이고 프런트 숨김은 UX일 뿐이다.
