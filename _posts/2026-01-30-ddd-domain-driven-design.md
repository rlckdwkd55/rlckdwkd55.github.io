DDD(Domain-Driven Design, 도메인 주도 설계)를 한 문장으로 말하면 "코드를 개발자 편한
구조가 아니라, 실제 업무가 돌아가는 방식대로 짜자"는 접근이다. 여기서 **도메인**은 어려운
말이 아니라 그냥 "이 소프트웨어가 다루는 업무 영역"이다. 쇼핑몰이면 주문·결제·배송이 도메인이고,
챗봇 서비스면 대화 세션·문서·검색이 도메인이다.

왜 이런 접근이 필요할까? 서비스가 커질수록 진짜 어려운 건 기술이 아니라 업무 규칙 자체다.
그런데 많은 코드가 이 규칙을 "DB 테이블에 뭘 넣을지", "프레임워크가 뭘 요구하는지" 관점으로만
옮겨 적다 보니, 정작 "왜 이렇게 동작해야 하는지"는 코드 어디에도 남지 않는다. 예를 들어
`Order`라는 클래스에 필드만 잔뜩 있고 "주문을 확정한다", "취소할 수 있는지 확인한다" 같은
행동은 죄다 서비스 파일에 흩어져 있는 경우다. 이렇게 데이터만 있고 행동(로직)이 빠진 걸
**빈약한 도메인 모델(Anemic Domain Model)** 이라 부른다. DDD는 반대로 이런 업무 규칙과
행동을 도메인 객체 안에 직접 넣어서, 코드만 봐도 업무가 어떻게 돌아가는지 알 수 있게 만들자는
것이다.

DDD를 만든 에반스(Eric Evans)는 이걸 두 단계로 나눠 설명한다.

- **전략적 설계**: "누구랑 어떤 말을 쓰고, 어디까지가 같은 모델인지" 큰 그림을 정하는 단계
- **전술적 설계**: 그 그림 안에서 실제로 클래스와 코드를 어떻게 짤지 정하는 단계

보통 DDD라고 하면 엔티티·값 객체 같은 코드 패턴(전술적 설계)만 떠올리기 쉬운데, 사실 그건
절반에 불과하고 전략적 설계도 똑같이 중요하다.

## 전략적 설계 — 유비쿼터스 언어

전략적 설계의 첫걸음은 **유비쿼터스 언어(Ubiquitous Language)** 다. 어려운 이름이지만
뜻은 단순하다. "기획자도, 도메인 전문가도, 개발자도 같은 단어를 같은 뜻으로 쓰자"는 것이다.

예를 들어 회의에서는 "회원"이라 부르는데, 코드에는 `UserAccount`, DB 테이블은 `tb_customer`,
화면(프런트)에는 `member`로 제각각 불린다고 해보자. 사람들이 대화할 때마다 "아 그게 그거였구나"
하고 머릿속에서 번역을 해야 하고, 이 과정에서 오해와 버그가 생긴다. 그래서 처음부터
"회원"이라는 하나의 단어를 정하고 회의·문서·코드 전부에서 그대로 쓰자는 것이 유비쿼터스
언어다.

이게 단순히 이름을 통일하자는 규칙만은 아니다. "발주랑 주문이 같은 건가요?"라고 묻고
답을 맞춰가는 과정 자체가, 그동안 서로 다르게 이해하고 있던 애매한 업무 규칙을 드러내 준다.

## 전략적 설계 — 바운디드 컨텍스트와 컨텍스트 맵

유비쿼터스 언어를 지키려다 보면 곧 한계에 부딪힌다. 같은 단어인데 상황(맥락)에 따라 뜻이
달라지는 경우가 있기 때문이다. 예를 들어 "상품"이라는 단어는 판매 담당자에게는 "가격·재고"를
뜻하지만, 배송 담당자에게는 "부피·무게"를 뜻한다. 이걸 억지로 하나의 거대한 `Product`
클래스에 다 담으려고 하면, 정작 어느 쪽에도 딱 맞지 않는 누더기 모델이 되어 버린다.

그래서 나온 개념이 **바운디드 컨텍스트(Bounded Context)** 다. "여기서부터 여기까지는
하나의 모델과 용어만 쓴다"는 경계선을 명확히 긋는 것이다. 그 경계 안에서는 유비쿼터스
언어를 지키되, 경계 밖에서는 같은 단어라도 다른 모델일 수 있다는 걸 인정한다. 즉 회사
전체를 아우르는 완벽한 하나의 모델을 만들려는 욕심을 버리고, 작지만 각자 안에서는 일관된
여러 개의 모델로 나누는 것이다.

이렇게 컨텍스트가 여러 개로 나뉘면, 이번엔 그 컨텍스트들이 서로 어떻게 데이터를 주고받고
협력할지를 정리해야 한다. 이 관계도를 **컨텍스트 맵(Context Map)** 이라 부르고, 흔히
쓰이는 통합 방식(패턴) 몇 가지가 있다.

| 패턴 | 의미 |
| --- | --- |
| Shared Kernel | 두 컨텍스트가 일부 모델을 공유(강한 결합, 신중히) |
| Customer/Supplier | 하류(고객)의 요구를 상류(공급자)가 반영해 주는 관계 |
| Conformist | 하류가 상류 모델을 그대로 따름 |
| Anti-Corruption Layer | 외부 모델을 내 모델로 번역하는 방어막을 둠 |
| Open Host Service | 공개 API/프로토콜로 다수 소비자에게 통합점 제공 |

이 중에서도 특히 유용한 건 **부패 방지 계층(Anti-Corruption Layer)** 이다. 외부 레거시
시스템이나 서드파티 API는 대개 우리 도메인 기준으로 보면 지저분하거나 구조가 다른
모델을 갖고 있다. 이걸 그대로 우리 코드에 끌어들이면 우리 도메인까지 지저분해지므로,
경계에 "번역 담당" 어댑터를 하나 두어 외부 모델을 우리 언어로 바꿔서 들여온다. 이 개념은
뒤에서 볼 헥사고날 아키텍처의 어댑터로 그대로 이어진다.

## 전술적 설계 — 빌딩 블록

여기부터는 실제 코드를 짤 때 쓰는 패턴들이다. 흔히 "DDD" 하면 떠올리는 게 바로 이것들이다.

- **엔티티(Entity)** — "고유한 번호(식별자)"로 구분되는 객체. 회원의 배송지 주소가
  바뀌어도 회원 번호가 같으면 "같은 회원"으로 취급한다. 즉 속성이 아니라 식별자로 같은지
  다른지를 판단한다.
- **값 객체(Value Object)** — 식별자가 따로 없고, 값 자체가 같으면 같은 것으로 보는
  객체. 금액, 좌표, 기간, 주소 같은 것들이다. 한 번 만들면 값이 바뀌지 않는 불변(immutable)
  객체로 만드는 게 보통이라, 여기저기서 안심하고 재사용할 수 있다.
- **애그리거트(Aggregate)** — "항상 같이 움직이고, 같이 일관성이 지켜져야 하는 객체
  묶음"이다. 예를 들어 주문과 주문 항목들은 따로 놀면 안 되니 하나의 애그리거트로 묶인다.
  외부에서는 이 묶음의 대표 격인 **애그리거트 루트**를 통해서만 내부에 접근할 수 있다.
- **리포지토리(Repository)** — 애그리거트를 저장하고 불러오는 창구. "이 데이터가 DB
  테이블 몇 개로 어떻게 저장되는지"는 도메인 코드가 몰라도 되게 감춰준다.
- **도메인 서비스(Domain Service)** — 엔티티 하나에 넣기는 애매하고, 여러 객체에
  걸쳐 있는 업무 로직을 담는 곳.
- **도메인 이벤트(Domain Event)** — "방금 이런 일이 일어났다"는 사실 자체를 표현하는
  객체. 예를 들어 "주문이 확정됨" 이벤트를 발행하면, 다른 컨텍스트(예: 배송)는 그 이벤트만
  받아서 처리하면 되므로 두 컨텍스트가 서로 직접 몰라도 된다.

이 중에서도 가장 중요한 건 애그리거트다. 존재 이유는 **불변식(invariant)**, 즉 "항상
지켜져야 하는 규칙"을 지키는 데 있다. 예를 들어 "주문 총액은 항상 항목 금액의 합과
같아야 한다"는 규칙이 있다고 해보자. 만약 아무나 주문과 항목을 각자 따로 수정할 수
있다면 이 규칙은 언제든 깨질 수 있다. 그래서 항목은 반드시 루트인 주문(`Order`)을
거쳐서만 바꿀 수 있게 막는다. 여기에 자주 놓치는 규칙 두 가지가 더 붙는다.

1. **애그리거트는 트랜잭션 경계다.** 하나의 트랜잭션에서는 애그리거트 하나만 바꾸는 걸
   원칙으로 한다. 여러 애그리거트를 한 트랜잭션으로 동시에 강하게 묶으려 하면, 애초에
   경계를 나눈 의미가 사라진다.
2. **다른 애그리거트는 객체 전체가 아니라 ID로만 참조한다.** `Order`가 `Member` 객체
   전체를 들고 있지 않고 `member_id`라는 숫자(또는 문자열)만 갖는 식이다. 이렇게 하면
   경계가 작게 유지되고, 주문 하나를 불러올 때 회원 정보까지 통째로 딸려 오는 걸 막을 수
   있다.

## 코드로 본 도메인 레이어

지금까지 나온 개념들이 실제 코드에서 어떻게 생겼는지, FastAPI 프로젝트를 예로 최소한만
정리한다. 여기 나오는 도메인 코드는 FastAPI나 SQLAlchemy 같은 프레임워크를 전혀 몰라도
되는 "순수 파이썬 코드"라는 점이 포인트다. 먼저 **값 객체**부터 본다. 값 객체는 값이
바뀌면 안 되므로 파이썬 dataclass의 `frozen=True` 옵션으로 잠가서, 한 번 만든 뒤에는
속성을 바꿀 수 없게 만든다.

```python
# app/domain/order/entity.py  (도메인 계층: 프레임워크 의존 X)
from dataclasses import dataclass, field
from enum import Enum

@dataclass(frozen=True)
class Money:
    amount: int
    currency: str = "KRW"

    def __post_init__(self):
        if self.amount < 0:
            raise ValueError("금액은 음수가 될 수 없다")

    def add(self, other: "Money") -> "Money":
        if self.currency != other.currency:
            raise ValueError("통화가 다르면 더할 수 없다")
        return Money(self.amount + other.amount, self.currency)
```

여기서 눈여겨볼 부분은 `Money` 클래스가 "음수 금액 금지", "통화가 다르면 더하기 금지" 같은
규칙을 스스로 갖고 있다는 점이다. 이 검증 로직이 서비스 코드가 아니라 도메인 객체 안에
있는 게 DDD의 핵심이다. 다음은 **엔티티**와 **애그리거트 루트**를 보자. `OrderItem`(주문
항목)은 루트인 `Order`(주문)를 거쳐야만 다룰 수 있고, "빈 주문은 확정 불가" 같은 불변식은
루트인 `Order`가 책임지고 지킨다.

```python
class OrderStatus(str, Enum):
    DRAFT = "DRAFT"
    PLACED = "PLACED"
    CANCELLED = "CANCELLED"

@dataclass
class OrderItem:              # 애그리거트 내부 엔티티
    product_id: int
    quantity: int
    unit_price: Money

@dataclass(eq=False)          # 동등성은 전 필드가 아니라 식별자로 판단한다
class Order:                  # 애그리거트 루트
    id: int | None
    member_id: int            # 다른 애그리거트는 ID로만 참조
    status: OrderStatus = OrderStatus.DRAFT
    items: list[OrderItem] = field(default_factory=list)

    def __eq__(self, other: object) -> bool:
        if not isinstance(other, Order):
            return NotImplemented
        if self.id is None or other.id is None:
            return self is other          # 아직 저장 전이면 인스턴스 동일성으로
        return self.id == other.id        # 저장 뒤엔 식별자만 본다

    def add_item(self, item: OrderItem) -> None:
        if self.status != OrderStatus.DRAFT:
            raise ValueError("확정된 주문은 항목을 바꿀 수 없다")
        self.items.append(item)

    def place(self) -> None:
        if not self.items:
            raise ValueError("빈 주문은 확정할 수 없다")
        self.status = OrderStatus.PLACED
```

`add_item`(항목 추가), `place`(주문 확정) 같은 행동이 규칙과 함께 엔티티 안에 들어 있다.
이게 앞서 말한 "빈약한 모델"과의 결정적 차이다. "빈 주문은 확정할 수 없다"는 규칙이
서비스 코드 여기저기에 흩어지지 않고, `Order` 클래스 한곳에 모여 있다.

`Order`에만 `eq=False`를 준 이유도 값 객체와 엔티티의 차이를 코드로 표현한 것이다.
`@dataclass`는 기본적으로 **모든 필드 값이 같으면 같다고 보는** `__eq__`(동등 비교 함수)를
자동으로 만들어 준다. 값 객체인 `Money`는 이게 정확히 맞는 동작이다(금액과 통화가 같으면
같은 값이니까). 하지만 엔티티인 `Order`는 다르다 — 배송지가 바뀌어도 같은 주문이어야
하므로, 모든 필드를 비교하는 기본 동작을 끄고(`eq=False`) 대신 식별자(`id`)만으로 같은지
판단하도록 직접 `__eq__`를 작성했다. 같은 데코레이터라도 값 객체와 엔티티에서 정반대로
써야 하는 지점이다.

**리포지토리**는 도메인 계층에는 "이런 기능이 있다"는 인터페이스(추상 클래스)만 둔다.
실제로 DB를 어떻게 조회하는지는 여기서 알 필요가 없다 — 도메인이 DB 세부사항을 모르게
하기 위해서다.

```python
# app/domain/order/repository.py  (인터페이스는 도메인 소유)
from abc import ABC, abstractmethod

class OrderRepository(ABC):
    @abstractmethod
    async def get(self, order_id: int) -> Order | None: ...

    @abstractmethod
    async def save(self, order: Order) -> Order: ...
```

이 인터페이스의 실제 구현체는 **인프라 계층**에 둔다. 여기서 비로소 SQLAlchemy 같은
구체적인 기술이 등장하고, 도메인 객체와 ORM 모델(DB 테이블에 대응하는 클래스)을 서로
변환하는 작업도 이 계층이 맡는다(DB 저장 관련 세부 내용은
[SQLAlchemy 비동기](https://rlckdwkd55.github.io/posts/sqlalchemy-async/)에서 다뤘다).

```python
# app/infra/order/repository_impl.py  (인프라 계층)
class SqlAlchemyOrderRepository(OrderRepository):
    def __init__(self, session):
        self._session = session

    async def get(self, order_id: int) -> Order | None:
        row = await self._session.get(OrderModel, order_id)   # ORM 모델
        return _to_domain(row) if row else None               # 도메인으로 번역
```

표현 계층(웹 요청을 받는 라우트)은 그냥 요청을 받아서 응용 계층에 넘겨주는 역할만 한다.
요청/응답 값을 검증하고 변환하는 건 [Pydantic](https://rlckdwkd55.github.io/posts/pydantic/)
모델이 담당하고, 도메인 모델(`Order` 같은 것)을 API 응답 형태로 그대로 노출하지 않는다.

## 계층/헥사고날 아키텍처와 의존성 방향

지금까지 나온 코드 조각들이 각각 어느 계층에 속하는지 그림으로 정리하면 이렇다.

```text
표현(route)        ← 요청/응답, HTTP 관심사
   │
응용(service)      ← 유스케이스 흐름 조립, 트랜잭션 경계
   │
도메인(entity)     ← 핵심 규칙 (프레임워크/DB 의존 X)
   ↑
인프라(repository impl) ── 도메인이 정의한 인터페이스를 구현
```

여기서 핵심 원칙은 **화살표(의존성)가 항상 도메인 쪽을 향하게** 하는 것이다. 즉 도메인은
웹이 뭔지, DB가 뭔지 전혀 몰라야 하고, 그 대신 바깥 계층(표현·인프라)이 도메인을 알고
참조한다. 리포지토리의 "인터페이스"는 도메인이 정의해서 소유하고, 그 "구현"은 인프라가
제공하는 구조 — 이게 바로 **의존성 역전(DIP)** 이다. 이렇게 해두면 나중에 DB나 웹
프레임워크를 통째로 바꾸더라도 핵심 업무 로직(도메인)은 건드릴 필요가 없다.
**헥사고날(포트-어댑터) 아키텍처** 도 결국 같은 이야기를 하는 개념이다. 도메인이 정의한
인터페이스를 "포트"라 부르고, 인프라가 그걸 실제로 구현한 것을 "어댑터"라 부른다. 앞서
나온 부패 방지 계층도 결국 어댑터의 한 종류다.

![](/assets/img/posts/backend/ddd/layers.png)

이름이 같아 헷갈리는 두 서비스는 역할이 다르다.

| 구분 | 응용 서비스(Application Service) | 도메인 서비스(Domain Service) |
| --- | --- | --- |
| 위치 | 응용 계층 | 도메인 계층 |
| 책임 | 유스케이스 조립, 트랜잭션 조율 | 순수 도메인 규칙(여러 객체 걸침) |
| 규칙 포함? | 규칙을 도메인에 위임 | 규칙 자체를 담음 |

여기서 조심할 점은, 응용 서비스가 업무 규칙을 직접 판단하기 시작하면 다시 빈약한 모델로
돌아간다는 것이다. 응용 서비스는 "누구를 불러서 무슨 순서로 시킬지"만 결정하고, "이게
가능한 상태인지" 같은 판단은 도메인 객체에게 물어봐야 한다.

이런 구조는 폴더를 나누는 방식에도 그대로 드러난다. `controllers/`, `services/`, `models/`처럼
기술 종류로 최상위 폴더를 나누면, "주문" 기능 하나를 바꾸는데도 세 폴더를 오가며 파일을
찾아야 한다. 반대로 `domain/order/`, `domain/member/`처럼 업무 단위로 최상위 폴더를 나누고
그 안에 `entity`, `repository`, `service`, `route`, `dto`를 두면, 주문 관련 변경은 대부분
`domain/order/` 폴더 하나로 끝난다. 이렇게 "함께 바뀌는 코드를 한곳에 모아두는 것"을
응집도가 높다고 하고, 이는 바운디드 컨텍스트라는 개념을 폴더 구조에 그대로 반영한 것이기도
하다.

## 흔한 오해들

**DDD는 폴더 구조가 아니다.** 도메인별로 폴더를 나누고 `entity`, `repository` 파일을
만들었다고 해서 저절로 DDD가 되는 게 아니다. 폴더 이름은 겉모습일 뿐이고, 진짜 중요한 건
그 안에 실제 업무 규칙과 유비쿼터스 언어가 담겨 있느냐다. 규칙은 전부 서비스 코드에 있고
엔티티는 그냥 데이터만 담는 껍데기라면, 폴더 이름만 그럴듯한 빈약한 모델일 뿐이다.

**모든 프로젝트에 DDD가 필요한 것도 아니다.** 단순 게시판처럼 CRUD(등록·조회·수정·삭제)만
하면 되는 도메인에 애그리거트·리포지토리 같은 추상을 억지로 끼워 넣으면 오히려 코드만
번거로워진다(보일러플레이트 비용). DDD가 진짜 빛을 발하는 곳은 규칙이 복잡한
**핵심 도메인(Core Domain)** 이다. 에반스도 모든 도메인에 똑같이 공들이지 말고, 핵심/지원/
일반 도메인으로 나눠서 정말 복잡하고 중요한 곳에만 역량을 집중하라고 말한다.

**엔티티·값 객체만 쓴다고 DDD가 아니다.** 전술적 패턴(엔티티, 값 객체 등)만 가져다 쓰고
유비쿼터스 언어나 바운디드 컨텍스트 같은 전략적 설계를 신경 쓰지 않으면, 결국 큰 그림 없이
하나의 거대하고 뒤죽박죽인 모델로 돌아가게 된다.

## 트레이드오프

| 얻는 것 | 치르는 비용 |
| --- | --- |
| 도메인 규칙이 한곳에 모여 이해·변경이 쉬움 | 초기 설계·추상화 비용이 큼 |
| 기술(웹/DB) 교체에 강함(의존성 역전) | 계층·매핑 코드(도메인↔ORM) 증가 |
| 도메인별 높은 응집, 변경 국소화 | 단순 CRUD에는 과설계 |
| 유비쿼터스 언어로 협업 오해 감소 | 도메인 전문가와의 지속적 대화 필요 |

DDD는 "쓴다/안 쓴다"로 켜고 끄는 스위치가 아니라, 얼마나 깊이 적용할지 정도(degree)를
조절하는 문제로 보는 게 좋다. 복잡한 핵심 도메인에는 애그리거트·도메인 서비스까지 깊게
적용하고, 단순한 도메인에는 얕게만 적용하면 된다. 폴더 구조를 지금 당장 바꾸지 못하더라도,
흩어져 있던 업무 규칙을 도메인 객체 안으로 조금씩 옮기는 것만으로도 충분히 얻는 게 있다.
