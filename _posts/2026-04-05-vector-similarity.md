벡터 검색은 결국 "질의 벡터와 가장 가까운 문서 벡터"를 찾는 일이다. 그런데 **가까움의
정의는 하나가 아니다.** 대표적으로 **코사인 유사도·내적(dot product)·유클리드 거리**
세 가지가 있고, 각각 재는 대상이 다르다.

[임베딩](https://rlckdwkd55.github.io/posts/embeddings-bge-m3/)으로 텍스트를 벡터로 바꿔
[Qdrant](https://rlckdwkd55.github.io/posts/qdrant/)에 넣을 때, 컬렉션의 거리 척도를
`Distance.COSINE`으로 둘지 `Distance.DOT`으로 둘지에 따라 검색 결과 순위가 달라진다. 그
차이의 근원은 세 지표가 서로 다른 것을 재기 때문이다. 이 글은 세 지표의 수식과 기하학적
의미를 손으로 계산해 확인하고, **정규화가 왜 이 셋을 사실상 하나로 묶는지**를 따라간다.

## 세 지표가 재는 것

표기부터 맞춘다. 벡터 `A = (a₁, a₂, …, aₙ)`, 노름(길이)은 `‖A‖ = √(Σ aᵢ²)`로 쓴다.

### 코사인 유사도 — 각도만 본다

```text
cos(θ) = (A·B) / (‖A‖ ‖B‖)        범위 -1 ~ 1 (1이면 같은 방향)
```

두 벡터가 이루는 **각도**로 유사도를 잰다. 분모의 `‖A‖ ‖B‖`가 크기를 나눠 없애기 때문에
**방향만** 남는다. 벡터를 아무리 길게 늘여도 방향이 같으면 코사인은 그대로 1이다.
"의미(방향)가 같으면 유사하다"는 직관과 잘 맞아, 텍스트 임베딩에서 기본값처럼 쓰인다.

### 내적 — 각도와 크기를 함께 본다

```text
A·B = Σ aᵢ·bᵢ = ‖A‖ ‖B‖ cos(θ)
```

내적은 정의상 **각도(cosθ)에 두 벡터의 크기까지 곱한** 값이다. 그래서 방향이 조금
어긋나 있어도 **벡터가 길면 내적이 커진다.** 크기 정보를 살리고 싶을 때 쓰지만, "긴 벡터가
유리해지는" 편향이 함께 따라온다는 뜻이기도 하다.

### 유클리드 거리 — 두 점 사이의 직선거리

```text
d(A, B) = √( Σ (aᵢ - bᵢ)² )        (작을수록 가까움)
```

좌표 공간에서 두 점을 잇는 **직선의 길이**다. 유사도가 아니라 거리라서, 값이
**작을수록** 가깝다는 점이 앞의 둘과 반대다.

## 정규화하면 셋이 한 순위로 묶인다

핵심은 여기다. 벡터를 **L2 정규화**(길이를 1로 맞추기, `Â = A / ‖A‖`)하면 세 지표가
사실상 같은 순위를 매긴다.

정규화된 두 벡터는 `‖Â‖ = ‖B̂‖ = 1`이다. 그러면 코사인의 분모가 1이 되어

```text
cos(θ) = Â·B̂        →  코사인 = 내적
```

즉 **정규화 후에는 내적이 곧 코사인**이다. 유클리드는 제곱을 풀어 보면 관계가 드러난다.

```text
d² = ‖Â - B̂‖² = ‖Â‖² + ‖B̂‖² - 2(Â·B̂)
   = 1 + 1 - 2 cos(θ)
   = 2(1 - cos θ)
```

`cos θ`가 커질수록 `d²`가 작아진다. 다른 항은 상수라 **코사인과 유클리드는 완벽한
단조(감소) 관계**다. 코사인으로 매긴 순위(내림차순)와 유클리드로 매긴 순위(오름차순)가
정확히 뒤집힌 채 일치한다. **정규화된 세계에서는 코사인·내적·유클리드가 top-k 순위를
똑같이 낸다.** 반대로 정규화가 섞여 있으면 지표마다 순위가 갈린다.

## 텍스트 임베딩에 코사인이 흔한 이유

정규화하면 결국 같아지는데도 관례적으로 코사인을 먼저 떠올리는 이유는, 정규화를
**깜빡해도** 코사인은 크기를 스스로 나눠 없애기 때문이다. 텍스트는 문서 길이가 제각각이라
임베딩 벡터의 노름도 들쭉날쭉하기 쉬운데, 코사인은 그 길이 편차에 **강건**하다.

내적에서 이 편차가 어떻게 사고를 치는지 손계산으로 본다. 질의 `q = (1, 0)`, 후보 둘.

```text
d1 = (1, 0)   ← q와 완전히 같은 방향, 짧음
d2 = (3, 3)   ← q와 45° 어긋났지만, 길다
```

- 내적: `q·d1 = 1`,  `q·d2 = 3·1 + 3·0 = 3`  →  **d2 우선**
- 코사인: `cos(q,d1) = 1 / (1·1) = 1.0`,  `cos(q,d2) = 3 / (1·√18) ≈ 0.707`  →  **d1 우선**

방향이 완벽히 맞는 `d1`을, 단지 더 길다는 이유로 `d2`가 내적에서 눌러 버린다. 문서
길이가 유사도를 왜곡하는 것이다. 코사인은 길이를 무시하고 방향만 보므로 `d1`을 제대로
1등으로 올린다. 정규화 습관이 아직 안 잡힌 단계에서 코사인이 안전한 기본값인 이유다.

## 손계산: 정규화 전후

`A = (3, 4)`, `B = (4, 3)`로 세 지표를 직접 계산한다. `‖A‖ = ‖B‖ = √25 = 5`.

```text
A·B     = 3·4 + 4·3 = 24
cos     = 24 / (5·5) = 0.96
d(A,B)  = √((3-4)² + (4-3)²) = √2 ≈ 1.414
```

이제 L2 정규화: `Â = (0.6, 0.8)`, `B̂ = (0.8, 0.6)`.

```text
Â·B̂     = 0.6·0.8 + 0.8·0.6 = 0.96      ← 코사인과 정확히 같음
d(Â,B̂)  = √((0.6-0.8)² + (0.8-0.6)²) = √0.08 ≈ 0.283
검산     = √(2(1-cos)) = √(2·0.04) = √0.08 ≈ 0.283   ← 위 공식과 일치
```

정규화 후 **내적이 코사인(0.96)과 같아지고**, 유클리드는 `√(2(1-cos))` 공식대로 나온다.
앞 절에서 유도한 관계가 숫자로 그대로 확인된다.

## 차원의 저주 한 스푼

임베딩은 보통 768·1024 같은 **고차원**이다. 차원이 높아지면 무작위 점들 사이의 거리가
서로 비슷해지는 **거리 집중(distance concentration)** 현상이 생긴다. 가장 먼 점과 가장
가까운 점의 거리 차이가 상대적으로 줄어들어, 유클리드 거리의 **절댓값** 자체는 정보가
흐려진다. 그래서 실무에서 중요한 건 거리의 절대 크기가 아니라 **상대 순위**이고, 방향에
집중하는 코사인이 고차원에서 비교적 안정적으로 동작한다.

## numpy로 확인

위 손계산을 그대로 코드로 옮기면 이렇다.

```python
import numpy as np

def cosine(a, b):
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

def dot(a, b):
    return float(np.dot(a, b))

def euclidean(a, b):
    return float(np.linalg.norm(a - b))

def l2_normalize(v):
    return v / np.linalg.norm(v)

q  = np.array([1.0, 0.0])
d1 = np.array([1.0, 0.0])
d2 = np.array([3.0, 3.0])

for name, d in [("d1", d1), ("d2", d2)]:
    print(f"{name}: cos={cosine(q, d):.3f}  dot={dot(q, d):.3f}  l2={euclidean(q, d):.3f}")
# d1: cos=1.000  dot=1.000  l2=0.000
# d2: cos=0.707  dot=3.000  l2=3.606   ← dot은 d2를, cos은 d1을 1등으로

# 정규화하면 dot == cos
qn, d2n = l2_normalize(q), l2_normalize(d2)
print(dot(qn, d2n), cosine(qn, d2n))   # 0.707... 0.707...
```

내적과 코사인이 서로 다른 후보를 1등으로 뽑다가, 정규화 후에는 내적이 코사인과 같은
값으로 수렴한다. `d2`의 유클리드 거리는 `√((1-3)² + (0-3)²) = √13 ≈ 3.606`이다.

## 벡터 DB에서의 거리 함수 선택

Qdrant는 컬렉션을 만들 때 거리 척도를 `Cosine / Dot / Euclid` 중에서 고른다. 여기서 앞의
결론이 실무 판단으로 이어진다.

- 임베딩 모델이 **코사인 기준으로 학습**됐다면(bge-m3를 비롯한 대부분) 코사인 계열을 쓴다.
- **벡터를 미리 L2 정규화해 저장**한다면 `Dot`이 유리할 수 있다. 정규화가 보장된 상태에서
  내적은 코사인과 순위가 동일한데, 매 비교마다 노름을 나누는 연산이 빠져 **더 가볍기**
  때문이다. (Qdrant는 `Cosine`을 고르면 업로드 시점에 내부적으로 정규화해 저장하므로,
  "미리 정규화 + Dot"과 사실상 같은 일을 한다.)
- 좌표적 거리 자체가 의미를 갖는 특수한 경우가 아니라면 `Euclid`를 굳이 먼저 고를 이유는
  적다. 정규화된 임베딩에선 어차피 코사인과 같은 순위다.

원칙은 **"정규화를 색인·질의에서 일관되게 맞추고, 모델 기준(대개 코사인)에 맞는 척도를
고른다"** 이다. 정규화만 일관되면 Cosine이냐 Dot이냐는 순위가 아니라 연산 비용의 문제로
좁혀진다.

## 세 지표 비교

| 지표 | 수식 | 재는 것 | 범위 / 방향 | 정규화 후 |
|---|---|---|---|---|
| 코사인 | (A·B)/(‖A‖‖B‖) | 각도(방향) | -1~1, 클수록 유사 | 그대로 |
| 내적 | Σ aᵢbᵢ | 각도+크기 | 제한 없음, 클수록 유사 | = 코사인 |
| 유클리드 | √Σ(aᵢ-bᵢ)² | 직선거리 | 0~∞, **작을수록** 유사 | √(2(1-cos)), 코사인과 단조 |

세 지표는 각각 코사인=각도, 내적=각도+크기, 유클리드=직선거리를 잰다. 그러나 L2 정규화로
길이를 1에 맞추면 내적은 코사인과 같아지고, 유클리드는 `d² = 2(1 - cos)`로 코사인과 완전한
단조 관계가 되어 셋이 같은 top-k 순위를 낸다. 텍스트 임베딩에 코사인이 흔한 것은 길이 편차에
강건하기 때문이며, 벡터 DB에서는 정규화를 색인·질의에 일관되게 맞추는 일이 먼저다. 그 뒤
Cosine이냐 Dot이냐는 순위가 아니라 연산 비용의 선택으로 좁혀진다.
