[임베딩](https://rlckdwkd55.github.io/posts/embeddings-bge-m3/)으로 텍스트를 벡터로 바꾸고 나면, 수백만 개의 벡터를 어디에 담고 어떻게 빨리 찾을지가 다음 문제가 된다.
[RAG 개요](https://rlckdwkd55.github.io/posts/rag/)에서 "벡터 DB에 넣고 검색한다"고 한 줄로 넘긴 그 부분을, 벡터 전용 DB인 Qdrant를 기준으로 정리한다.
벡터를 리스트에 담아 넘파이로 코사인을 전부 도는 방식은 문서 수천 개까지는 문제없지만, 대상이 수십만·수백만으로 늘면 질의 하나에 수 초가 걸리고 재시작 시 인덱스가 통째로 사라진다.

## 왜 벡터 전용 DB인가

임베딩 검색의 본질은 질의 벡터와 가장 가까운 top-k 벡터를 찾는 것이다.
전체 벡터를 한 번씩 다 비교하는 **완전 탐색(brute force)** 은 정확하지만 벡터 개수 N에 정비례해 느려진다. 1024차원 곱셈·합을 벡터마다 도니, N이 수백만이면 질의당 수십억 번 연산이다.
그래서 나온 것이 **ANN(Approximate Nearest Neighbor, 근사 최근접 이웃)** 이다. 100% 정확한 최근접 대신 거의 정확한 결과를 훨씬 빠르게 얻는 트레이드오프이며, 관건은 정확도(recall)와 속도를 조절할 수 있느냐다.

ANN만 필요하면 FAISS 같은 라이브러리로도 가능하다. 그러나 실서비스에는 라이브러리만으로 부족한 것들이 있다.

- **영속성** — 프로세스가 죽어도 인덱스가 디스크에 안전하게 남아야 한다.
- **메타데이터 필터** — "카테고리가 X인 문서 중에서만" 같은 조건을 벡터 검색과 **함께** 걸어야 한다.
- **CRUD** — 문서가 계속 추가·수정·삭제되므로, 매번 전체 인덱스를 다시 만들 수 없다.
- **운영** — 스냅샷, 수평 확장, 모니터링.

**Qdrant** 는 이것들을 묶어 주는 벡터 DB다(Rust로 작성, REST·gRPC 제공). 특히 payload 필터를 인덱스 탐색에 녹여 넣은 점이 다른 선택지와 갈린다.

## 데이터 모델: Collection / Point / Payload

Qdrant의 모델은 세 층으로 단순하다.

- **Collection(컬렉션)** — 벡터들의 논리적 묶음(RDB의 테이블에 해당). **벡터 차원**과 **거리 척도**를 컬렉션 단위로 고정하며, 한번 정하면 이 둘은 바꿀 수 없다.
- **Point(포인트)** — 저장 단위. `id + vector + payload` 로 구성된다.
- **Payload** — 포인트에 딸린 임의의 JSON 메타데이터(원문, 카테고리, 문서 ID, 날짜 등). 필터링과 결과 표시에 쓴다.

거리 척도는 `Cosine`, `Dot`, `Euclid` 중에서 고른다. 임베딩 모델이 학습된 기준(대개 코사인)에 맞춰야 하며, 이 선택의 이유는 [벡터 유사도 지표](https://rlckdwkd55.github.io/posts/vector-similarity/)에서 따로 다뤘다. bge-m3처럼 정규화된 임베딩이면 Cosine이 무난하다.

```python
from qdrant_client import QdrantClient
from qdrant_client.models import Distance, VectorParams, PointStruct

client = QdrantClient(url="http://localhost:6333")

# 컬렉션 생성: 차원(bge-m3 = 1024)과 거리 척도를 여기서 고정한다
client.create_collection(
    collection_name="docs",
    vectors_config=VectorParams(size=1024, distance=Distance.COSINE),
)
```

주의할 점 하나. **Qdrant의 포인트 id는 부호 없는 정수(u64) 또는 UUID만 허용한다.** `"doc42-chunk3"` 같은 문자열 id는 거부되므로, id는 UUID로 두고 문서·청크 정보는 **payload에 담는** 패턴이 굳어진다.

```python
import uuid

client.upsert(
    collection_name="docs",
    points=[
        PointStruct(
            id=str(uuid.uuid4()),              # u64 또는 UUID만 허용
            vector=embedding,                  # 길이 1024 실수 리스트
            payload={
                "doc_id": 42,
                "chunk": 3,
                "category": "law",
                "text": "원문 청크 ...",
            },
        ),
    ],
)
```

`upsert` 는 있으면 갱신, 없으면 삽입이다. 같은 id로 다시 넣으면 벡터와 payload가 통째로 덮어써진다. 이 멱등성이 뒤의 재색인·동기화에서 핵심이 된다.

## 검색: 벡터 유사도 + payload 필터

Qdrant를 쓰는 핵심 이유가 여기 있다. **벡터 유사도와 조건 필터를 한 번의 질의로 결합**한다. "카테고리가 law인 문서 중 의미적으로 가까운 5개" 같은 요구를, 검색 후 후처리가 아니라 검색 단계에서 함께 푼다.

```python
from qdrant_client.models import Filter, FieldCondition, MatchValue, Range

hits = client.query_points(
    collection_name="docs",
    query=query_embedding,                     # 질의 벡터
    limit=5,
    query_filter=Filter(
        must=[
            FieldCondition(key="category", match=MatchValue(value="law")),
            FieldCondition(key="year", range=Range(gte=2020)),
        ]
    ),
).points

for h in hits:
    print(h.id, round(h.score, 4), h.payload["text"][:30])
```

조건에 맞는 것만 먼저 골라 그 안에서 ANN을 하는 방식으로 이해하기 쉽지만, 그렇게 하면 조건이 빡빡할 때 HNSW 그래프가 **끊겨** 후보를 못 찾고 조건이 헐거우면 브루트포스로 떨어진다.
Qdrant는 이를 **filterable HNSW**로 푼다. 필터 조건을 그래프 탐색 **중에** 평가해, 조건에 맞는 이웃만 따라가도 연결이 유지되도록 인덱스를 짓는다. 덕분에 필터를 걸어도 대체로 ANN 속도를 유지한다. 대신 조건이 걸리는 payload 필드에는 **payload 인덱스**를 만들어 둬야 필터가 빠르다.

```python
from qdrant_client.models import PayloadSchemaType

client.create_payload_index(
    collection_name="docs",
    field_name="category",
    field_schema=PayloadSchemaType.KEYWORD,
)
```

## HNSW 파라미터: m, ef_construct, ef

Qdrant의 ANN 엔진은 **HNSW(Hierarchical Navigable Small World)** 그래프다. 계층 그래프를 위에서부터 타고 내려가며 후보를 좁혀, 정확도를 거의 유지하면서 탐색량을 로그 규모로 줄인다. 조절 손잡이는 세 개이고, 역할로 나누면 이렇다.

| 파라미터 | 언제 작용 | 크게 하면 | 작게 하면 |
|----------|-----------|-----------|-----------|
| `m` | 색인(그래프 구조) | 노드당 연결↑ → recall↑, 메모리·색인시간↑ | 가볍지만 recall↓ |
| `ef_construct` | 색인(그래프 품질) | 더 촘촘히 연결 탐색 → 품질↑, 색인 느림 | 색인 빠르지만 그래프 성김 |
| `ef` (hnsw_ef) | 검색 | 후보 폭↑ → recall↑, 질의 느림 | 질의 빠르지만 recall↓ |

핵심은 **`m`·`ef_construct`가 "만들 때 한 번" 정하는 그래프 골격**이고, **`ef`는 "검색할 때마다" 정확도-지연을 저울질하는 값**이라는 점이다. 색인은 좋은 품질로 한 번 지어 두고 `ef`만 질의 상황에 따라 조절하는 식으로 운영한다.

```python
from qdrant_client.models import HnswConfigDiff, SearchParams

# 색인 시: 골격 파라미터
client.create_collection(
    collection_name="docs",
    vectors_config=VectorParams(size=1024, distance=Distance.COSINE),
    hnsw_config=HnswConfigDiff(m=16, ef_construct=100),
)

# 검색 시: ef만 질의별로 조절 (정확도가 중요한 질의는 크게)
hits = client.query_points(
    collection_name="docs",
    query=query_embedding,
    limit=5,
    search_params=SearchParams(hnsw_ef=128),
).points
```

`m=16`, `ef_construct=100`이 무난한 출발점이다. recall이 아쉬우면 먼저 `ef`(검색)를 올리고, 그래도 부족하면 `m`을 키워 재색인하는 순서가 좋다. `m`을 무작정 키우면 메모리가 눈에 띄게 불어난다.

## Named Vectors: 한 컬렉션에 dense + sparse

한 포인트에 **이름 붙인 여러 벡터**를 담을 수 있고, 대표적 쓰임이 **하이브리드 검색**이다. [bge-m3](https://rlckdwkd55.github.io/posts/embeddings-bge-m3/)는 한 모델로 dense(의미) 벡터와 sparse(어휘 가중치) 벡터를 동시에 낼 수 있는데, 이 둘을 같은 컬렉션에 나란히 저장한다.

```python
from qdrant_client.models import SparseVectorParams, SparseVector

client.create_collection(
    collection_name="hybrid_docs",
    vectors_config={
        "dense": VectorParams(size=1024, distance=Distance.COSINE),
    },
    sparse_vectors_config={
        "sparse": SparseVectorParams(),
    },
)

client.upsert(
    collection_name="hybrid_docs",
    points=[
        PointStruct(
            id=str(uuid.uuid4()),
            vector={
                "dense": dense_vec,                                    # 의미 벡터
                "sparse": SparseVector(indices=idx, values=vals),      # 어휘 벡터
            },
            payload={"text": "..."},
        ),
    ],
)
```

sparse 벡터는 사실상 [BM25](https://rlckdwkd55.github.io/posts/bm25/)식 어휘 매칭을 벡터 형태로 담은 것이라 dense의 의미 매칭과 성격이 다르다. 스케일이 전혀 다른 두 결과를 하나의 순위로 융합하는 방법은 [RRF](https://rlckdwkd55.github.io/posts/rrf/)에서 따로 정리했다. Qdrant는 서버 단에서 이 융합(Query API의 fusion)도 지원한다.

## 양자화로 메모리 줄이기: Scalar / Product

벡터를 원본 float32로 다 들고 있으면 메모리가 벅차다. 1024차원 × 4바이트 = 벡터당 4KB, 1천만 개면 40GB다. **양자화(quantization)** 는 벡터를 더 적은 비트로 근사 표현해 메모리를 줄이는 기법이다.

| 방식 | 압축 아이디어 | 대략적 절감 | 특징 |
|------|---------------|-------------|------|
| **Scalar (INT8)** | 각 차원 float32 → int8 | 약 4배 | 구현·정확도 균형 좋음, 기본 선택 |
| **Product (PQ)** | 벡터를 조각내 코드북으로 치환 | 최대 수십 배 | 절감 크지만 정확도 손실·연산 복잡 |

핵심은 **양자화된 벡터로 후보를 빠르게 추린 뒤, 원본 벡터로 다시 정밀 채점(rescore)한다**는 2단계 구조다. 원본을 디스크에 두고 양자화본만 RAM에 올리면(`always_ram=True`), 메모리를 아끼면서 정확도 손실을 rescore로 만회한다.

```python
from qdrant_client.models import ScalarQuantization, ScalarQuantizationConfig, ScalarType

client.create_collection(
    collection_name="docs",
    vectors_config=VectorParams(size=1024, distance=Distance.COSINE),
    quantization_config=ScalarQuantization(
        scalar=ScalarQuantizationConfig(
            type=ScalarType.INT8,
            quantile=0.99,        # 이상치를 잘라 양자화 구간을 안정화
            always_ram=True,      # 양자화본은 RAM에 상주
        )
    ),
)
```

대개 **Scalar INT8부터** 시작하는 게 무난하다. 4배 절감에 정확도 손실이 작고, rescore를 켜면 체감 품질 저하가 거의 없다. Product 양자화는 절감폭이 크지만 코드북 학습·연산 부담과 recall 저하가 커서, 메모리가 극단적으로 빡빡할 때만 저울질한다.

## 재색인·동기화 주의점

개념보다 운영에서 더 자주 발목을 잡는 건 **데이터가 계속 바뀔 때** 생기는 문제들이다.

- **거리 척도·차원은 못 바꾼다.** 컬렉션 생성 시 고정이라, 임베딩 모델을 바꿔 차원이나 학습 기준이 달라지면 **새 컬렉션을 만들어 전량 재색인**해야 한다. 기존 벡터에 새 모델 벡터를 섞으면 좌표계가 달라 검색이 조용히 망가진다.
- **재색인 순서.** 원본 문서를 지우고 다시 넣는 사이에 검색이 들어오면 사용자는 텅 빈 결과를 본다. 무중단 교체의 순서와 스위칭은 [재임베딩 순서](https://rlckdwkd55.github.io/posts/reembedding-order/)에서 따로 다뤘다.
- **id 안정성이 동기화의 열쇠.** upsert가 멱등이므로, **같은 문서 청크는 항상 같은 id로** 매핑되게 해 두면(예: `doc_id+chunk`로 UUID를 결정적으로 생성) 재색인이 그냥 덮어쓰기가 된다. id가 매번 랜덤이면 옛 포인트가 남아 중복 결과를 낸다.
- **삭제 동기화.** 원본에서 사라진 문서는 Qdrant에서도 지워야 한다. payload 조건으로 지우는 방식이 편하다. 이 CRUD ↔ 벡터 동기화를 챗봇 시나리오 관리에 적용한 사례는 [시나리오 관리](https://rlckdwkd55.github.io/posts/scenario-management/)에 정리했다.

```python
from qdrant_client.models import FilterSelector

# 원본에서 삭제된 문서를 payload 조건으로 함께 제거
client.delete(
    collection_name="docs",
    points_selector=FilterSelector(
        filter=Filter(
            must=[FieldCondition(key="doc_id", match=MatchValue(value=42))]
        )
    ),
)
```

벡터 DB는 한 번 넣고 끝나는 저장소가 아니라 원본 데이터와 계속 맞춰 나가는 대상이다.
id 설계와 upsert 멱등성을 초반에 잡아 두지 않으면, 뒤에서 유령 포인트와 중복 결과를 쫓게 된다.
