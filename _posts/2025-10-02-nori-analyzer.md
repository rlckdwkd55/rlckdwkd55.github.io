검색은 문서 원문을 훑지 않는다. **분석기가 만들어 둔 텀(term)** 끼리 정확히 일치하는지를
본다([역색인](https://rlckdwkd55.github.io/posts/elasticsearch-inverted-index/) 참고). 이
구조 위에서 한국어는 표준 토크나이저만으로 검색이 깨진다.

예를 들어 "학교에서 회의를 했다"라는 문서를 기본 분석기로 색인하면 텀은 `학교에서`,
`회의를`, `했다` 가 된다. 사용자가 검색창에 넣은 `학교` 라는 텀은 이 목록 어디에도 없다.
글자는 겹치는데 텀이 다르니, 검색 입장에선 존재하지 않는 단어다. 이 문제를 푸는 것이 ES의
공식 한국어 형태소 분석기 **Nori** 다.

## 표준 토크나이저가 하는 일

ES 기본 분석기(standard analyzer)의 `standard` 토크나이저는 **유니코드 텍스트 분할(UAX
#29)** 규칙을 따른다. 공백과 구두점을 경계로 단어를 자른다는 뜻이다. 영어는 이걸로 충분하다.
`I go to school` 은 공백만으로 `i`, `go`, `to`, `school` 로 나뉘고 `school` 검색이 그대로
맞는다.

문제는 한국어가 **교착어**라는 데 있다. 명사에 조사가, 동사 어간에 어미가 줄줄이 달라붙어 한
어절을 이룬다. 공백은 어절 사이에만 있지, 어절 안의 형태소는 갈라 주지 못한다.

```text
"학교"  "학교에서"  "학교를"  "학교로"  "학교까지"
  → 표준 토크나이저에겐 전부 다른 5개의 텀
```

사람 눈엔 다 같은 "학교"지만 텀 단위로는 완전히 별개다. 조사·어미를 떼어 내고 **어근(형태소)**
만 텀으로 남겨야 하며, 이 일을 하는 것이 형태소 분석기다.

## Nori의 구조

Nori는 ES가 공식 제공하는 한국어 형태소 분석 플러그인(`analysis-nori`)이다. 내부적으로
**mecab-ko-dic** 사전을 Lucene용으로 빌드해 쓰며, 사전과 통계 정보를 근거로 문장을 형태소로
분해하고 각 형태소에 **품사(POS) 태그**를 붙인다.

여느 ES 분석기와 같이 Nori도 **character filter → tokenizer → token filter** 파이프라인으로
동작한다. 핵심은 `nori_tokenizer` 하나이고, 나머지는 그 결과를 다듬는 토큰 필터다.

| 구성요소 | 종류 | 역할 |
|---|---|---|
| `nori_tokenizer` | tokenizer | 문장을 형태소로 분해, 복합명사 분해 결정 |
| `nori_part_of_speech` | token filter | 조사·어미 등 불필요한 품사 제거 |
| `nori_readingform` | token filter | 한자를 한글 독음으로 변환 |
| `nori_number` | token filter | 한글 수사를 아라비아 숫자로 정규화 |

## nori_tokenizer와 decompound_mode

`nori_tokenizer`의 가장 중요한 옵션은 **`decompound_mode`** 로, 복합명사를 어떻게 쪼갤지
결정한다. 복합명사는 여러 명사가 붙어 만들어진 단어다. `삼성전자` 는 `삼성` + `전자` 로
이루어진 복합명사이며, 이걸 그대로 둘지 잘게 쪼갤지가 검색 품질을 크게 가른다.

| 모드 | `삼성전자` 색인 결과 | 설명 |
|---|---|---|
| `none` | `삼성전자` | 분해하지 않고 원형만 |
| `discard` | `삼성`, `전자` | 분해하고 원형은 버림 (기본값) |
| `mixed` | `삼성전자`, `삼성`, `전자` | 분해형과 원형을 **모두** 보존 |

기본값은 `discard` 다. 재현율을 높이려고 `mixed` 를 쓰는 경우가 많다. `mixed` 면 사용자가
"삼성전자"로 검색하든 "전자"로 검색하든 문서가 걸린다. 대신 원형과 분해형이 모두 색인되니 색인
크기와 노이즈가 늘어난다.

## _analyze로 확인하기

`_analyze` API로 실제 분해 결과를 찍어 보면 동작이 분명해진다. 복합명사 하나를 `mixed` 로
돌린다.

```text
POST /_analyze
{
  "tokenizer": {
    "type": "nori_tokenizer",
    "decompound_mode": "mixed"
  },
  "text": "삼성전자검색엔진"
}
```

결과 텀은 대략 다음과 같다.

```text
삼성전자, 삼성, 전자, 검색, 엔진
```

`삼성전자` 는 복합명사라 원형과 분해형이 함께 나오고, `검색엔진` 은 사전에 없는 조합이라 `검색`
과 `엔진` 두 명사로 갈린다. "검색", "엔진", "삼성전자" 어느 쪽으로 검색해도 문서가 잡힌다.

품사 태그까지 보려면 `explain: true` 를 준다. 조사·어미가 어떻게 붙는지 온전한 문장으로 확인한
결과다.

```text
입력: "학교에서 책을 빌렸다"

텀      품사    처리
────    ────    ────────────
학교    NNG     유지 (일반명사)
에서    J       제거 (조사)
책      NNG     유지 (일반명사)
을      J       제거 (조사)
빌리    VV      유지 (동사 → 어간 복원)
었      E       제거 (선어말어미)
다      E       제거 (종결어미)
```

두 가지가 핵심이다. 첫째, 조사 `에서`·`을` 와 어미 `었`·`다` 가 별도 형태소로 분리된다. 둘째,
`빌렸다` 는 활용형인데 **어간 `빌리` 로 원형이 복원**된다. 뒤의 품사 필터로 조사·어미만 걷어
내면 `학교`, `책`, `빌리` 라는 텀만 남는다. "학교"로도 "책"으로도 "빌리다"로도 이 문장이
검색된다.

## 재현율·정밀도 트레이드오프

`decompound_mode` 선택은 결국 **재현율(recall)과 정밀도(precision)의 트레이드오프**다. 잘게
쪼갤수록 더 많은 질의에 걸리지만(재현율↑), 엉뚱한 문서까지 걸린다(정밀도↓).

| 모드 | 재현율 | 정밀도 | 색인 크기 | 대표적 쓰임 |
|---|---|---|---|---|
| `none` | 낮음 | 높음 | 작음 | 정확한 고유명사 매칭이 중요할 때 |
| `discard` | 중간 | 중간 | 작음 | 일반적인 기본 선택 |
| `mixed` | 높음 | 낮음 | 큼 | 놓치면 안 되는 검색(재현율 우선) |

`한국전력` 을 `mixed` 로 쪼개면 `전력` 만으로도 걸리는데, 이러면 "전력 사용량", "전력 계통"
같은 무관한 문서까지 딸려 온다. 반대로 `none` 이면 "한국전력"이라고 통째로 쳐야만 걸린다. 정답은
없고 **서비스의 검색 성격**에 달렸다. 실무에서는 이 트레이드오프를
[BM25](https://rlckdwkd55.github.io/posts/bm25/) 랭킹과 함께 다룬다. 넓게 걸리게 해 두고(재현율)
랭킹으로 관련도 높은 문서를 위로 올리는 전략이 무난하다.

## 품사 필터로 노이즈 제거

`nori_tokenizer` 가 붙인 품사 태그를 활용하는 것이 `nori_part_of_speech` 토큰 필터다.
**`stoptags`** 에 나열한 품사의 형태소를 색인에서 제외한다. 조사(J)·어미(E)처럼 검색 변별력이
없는 형태소를 걸러 내는 역할이다.

```text
"nori_pos_filter": {
  "type": "nori_part_of_speech",
  "stoptags": ["E", "IC", "J", "MAG", "MAJ", "MM", "SP", "SSC",
               "SSO", "SC", "SE", "XPN", "XSA", "XSN", "XSV",
               "UNA", "NA", "VSV"]
}
```

위 목록이 Nori의 기본 `stoptags` 다. 주로 조사·어미·부사·접사처럼 그 자체로는 검색 키워드가
되기 어려운 품사들이며, 명사(NNG/NNP)·동사(VV)·형용사(VA)는 남는다. 도메인에 따라 이 목록을
조정한다. 부사(MAG)가 검색에 의미 있는 서비스라면 목록에서 빼서 살려 두는 식이다.

## 사용자 사전으로 도메인 용어 살리기

형태소 분석은 사전에 의존한다. 사전에 없는 신조어·고유명사·업계 복합어는 엉뚱하게 쪼개진다.
가령 제품명 `클라우드정산` 을 넣으면 `클라우드`, `정산` 으로 갈려 "클라우드정산" 전체 매칭이
흐트러진다. 이때 **사용자 사전(user dictionary)** 으로 원하는 분해 방식을 명시한다.

`user_dictionary_rules` 형식은 mecab 규칙과 같다. 한 줄에 표층형만 적으면 **쪼개지 않고 한
단어로** 유지하고, 뒤에 분해형을 공백으로 붙이면 그 규칙대로 쪼갠다.

```text
클라우드정산
빅데이터플랫폼 빅데이터 플랫폼
정산센터 정산 센터
```

- `클라우드정산` — 분해 없이 한 텀으로 유지
- `빅데이터플랫폼` — `빅데이터` + `플랫폼` 으로 강제 분해
- `정산센터` — `정산` + `센터` 로 분해

주의할 점은 사전이나 분석 설정을 바꿔도 **기존에 색인된 문서는 옛 분석 결과 그대로** 라는 것이다.
분석기는 색인 시점에 적용되기 때문이다. 사전을 갱신했다면 **재색인(reindex)** 해야 검색에
반영된다.

동의어를 형태소 분석으로 해결하려 해선 안 된다. "노트북 = 랩탑" 같은 동의어는 별도의
[synonym 필터](https://rlckdwkd55.github.io/posts/synonym-graph/)가 담당한다. Nori는 형태를
쪼개는 역할, synonym은 의미를 이어 주는 역할로 관심사가 다르다.

## 부가 필터: readingform, number

- **`nori_readingform`** — 한자를 한글 독음으로 바꾼다. `中國` 을 색인하면 `중국` 텀이 나와,
  한글로 검색해도 한자 문서가 걸린다.
- **`nori_number`** — 한글로 쓴 수를 아라비아 숫자로 정규화한다. `이십삼` → `23` 처럼. 숫자
  표기가 뒤섞인 문서에서 유용하다.

두 필터는 필수가 아니며, 다루는 문서에 한자·수사가 섞여 있을 때 정밀도를 올리려고 파이프라인에
끼워 넣는다.

## 색인 분석기와 검색 분석기

같은 필드라도 **색인용(`analyzer`)과 검색용(`search_analyzer`)을 분리**할 수 있다. 색인은
`mixed` 로 넓게 쪼개 재현율을 확보하고, 검색은 조금 더 보수적으로 분석해 질의를 다듬는 식이다.
다만 원칙은 하나다. **둘의 분석 결과가 짝이 맞아야** 한다. 색인 텀과 검색 텀이 서로 다른 규칙으로
만들어지면, 그 순간 다시 "학교로 학교에서를 못 찾는" 처음의 문제로 돌아간다.

이 짝 맞춤이 Nori 설정의 마지막 검증 지점이다. `decompound_mode`, `stoptags`, 사용자 사전을
어떻게 조합하든, 색인과 검색 양쪽에서 같은 텀이 나오는지를 `_analyze` 로 확인하고 나서야 설정이
끝난다.
