JWT(JSON Web Token)는 인증 정보를 토큰 문자열 안에 담아 주고받는 방식이다. 로그인 후
서버가 발급한 토큰을 클라이언트가 요청 헤더에 실어 보내면 인증이 이뤄진다. 세션 인증과
달리 서버가 인증 상태를 저장하지 않으며, 이 무상태(stateless) 성질에서 장점과 한계가
함께 나온다. 흔한 오해 하나를 먼저 짚어 두면, 토큰의 서명은 내용을 숨기는 암호화가 아니라
위변조를 막는 검증 장치다.

## 세션 인증과의 차이

전통적인 세션 인증은 서버가 상태를 들고 있다. 로그인하면 서버가 세션을 만들어 메모리나
DB, Redis에 저장하고, 클라이언트에는 세션 ID만 쿠키로 준다. 이후 요청마다 서버는 그
세션 ID로 저장소를 조회해 누구인지 확인한다. 인증 상태의 원본이 서버에 있는 구조다.

JWT는 반대다. 서버가 아무것도 저장하지 않는다. 누구인지를 토큰 안에 적어 클라이언트에게
통째로 넘기고, 그 토큰에 **서명**만 해 둔다. 다음 요청에서 서버는 저장소를 뒤지는 게
아니라 토큰의 서명이 자신이 만든 것이 맞는지만 계산한다. 서명이 맞으면 토큰 안의 사용자
정보를 신뢰한다.

| 구분 | 세션 인증 | JWT(무상태) |
| --- | --- | --- |
| 상태의 원본 | 서버 저장소 | 토큰 자체 |
| 요청당 검증 | 저장소 조회 필요 | 서명 계산만 (조회 X) |
| 수평 확장 | 세션 공유/스티키 세션 필요 | 서버가 키만 알면 됨 |
| 즉시 무효화 | 저장소에서 지우면 끝 | 어렵다 (뒤에서 다룸) |

무상태의 장점은 명확하다. 서버를 여러 대로 늘려도 세션을 공유할 필요가 없고, 각 서버가
서명 키만 알면 어떤 서버로 요청이 가든 토큰을 검증한다. 대가는 표의 마지막 줄,
**즉시 무효화가 어렵다**는 점이다.

## 구조: 점 두 개로 나뉜 세 조각

JWT는 `xxxxx.yyyyy.zzzzz` 형태로, 점 두 개가 세 부분을 가른다. 앞의 두 조각은 각각
JSON을 **Base64URL로 인코딩**한 것이고, 마지막이 서명이다.

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9   ← Header
.eyJzdWIiOiIxMjM0IiwiZXhwIjoxNzE2NX0     ← Payload
.dQw4w9WgXcQ-DUMMYSIGNATUREVALUE1234     ← Signature (더미)
```

**Header**는 토큰 타입과 서명 알고리즘을 담는다.

```json
{ "alg": "HS256", "typ": "JWT" }
```

**Payload**는 클레임(claim), 즉 담고 싶은 정보다. 사용자 ID, 만료 시각 같은 것들이 들어간다.

```json
{ "sub": "1234", "role": "user", "iat": 1716500000, "exp": 1716503600 }
```

여기서 가장 많이 오해하는 지점이 있다. **Base64URL은 인코딩이지 암호화가 아니다.** 키도
필요 없고, 누구나 즉시 디코드해 원문을 볼 수 있다. 실제로 위 payload를 디코드하면 그대로
JSON이 나온다.

```python
import base64, json
payload_b64 = "eyJzdWIiOiIxMjM0IiwiZXhwIjoxNzE2NX0"
# base64url 패딩 보정 후 디코드
padded = payload_b64 + "=" * (-len(payload_b64) % 4)
print(json.loads(base64.urlsafe_b64decode(padded)))
# → {'sub': '1234', 'exp': 17165...}
```

그래서 **payload에는 비밀을 담으면 안 된다.** 비밀번호, 주민번호, API 키 같은 값은 금물이다.
토큰을 가진 사람은 서버 키가 없어도 payload 내용을 전부 읽을 수 있다.

**Signature**는 위변조를 막는 장치다. `header`와 `payload`(각각 Base64URL 인코딩한 값)를
점으로 이어 붙인 문자열을 **비밀키로 서명**한 결과다.

```text
Signature = HMACSHA256( base64url(header) + "." + base64url(payload), secret )
```

핵심은 "내용은 공개, 위조는 불가"다. 누구나 payload를 읽을 수 있지만, `role`을 `admin`으로
바꾸는 순간 서명이 어긋나고 서버는 그 토큰을 거부한다. 서명은 내용을 숨기는 게 아니라
바뀌지 않았음을 보증한다.

## 검증 원리와 서명 알고리즘

서버가 토큰을 받으면 하는 일은 두 가지다.

1. header/payload를 가지고 **서명을 다시 계산**해, 토큰에 붙어 온 서명과 일치하는지 확인
2. `exp`(만료 시각)가 지나지 않았는지 등 클레임 확인

둘 다 통과하면 payload의 사용자와 권한을 신뢰한다. DB 조회가 한 번도 없다는 점이 확장에
유리한 이유다.

서명 방식은 크게 두 갈래이며, 이 선택이 은근히 중요하다.

| 항목 | HS256 (대칭) | RS256 (비대칭) |
| --- | --- | --- |
| 키 구성 | 비밀키 하나 | 개인키(서명) + 공개키(검증) |
| 서명/검증 주체 | 같은 키로 둘 다 | 개인키로 서명, 공개키로 검증 |
| 키 공유 | 검증하려면 비밀키를 공유해야 함 | 공개키만 배포하면 됨 |
| 적합한 상황 | 단일 서비스가 발급·검증 | 발급자와 검증자가 분리(마이크로서비스, OAuth) |

하나의 백엔드가 토큰을 발급하고 검증까지 한다면 HS256이 단순하고 충분하다. 반면 인증
서버가 발급하고 여러 서비스가 각자 검증해야 한다면, 비밀키를 모두에게 뿌리는 것은
위험하므로 RS256으로 공개키만 배포하는 게 맞다.

## 표준 클레임

payload에 아무 이름이나 넣어도 되지만, RFC 7519가 정한 **등록 클레임(registered claim)**이
있다. 이름이 짧은 것은 토큰 크기를 줄이기 위해서다.

| 클레임 | 뜻 | 용도 |
| --- | --- | --- |
| `iss` | issuer | 발급자 |
| `sub` | subject | 토큰의 주체(보통 사용자 ID) |
| `exp` | expiration | 만료 시각 이후 거부 |
| `iat` | issued at | 발급 시각 |
| `nbf` | not before | 이 시각 이전엔 유효하지 않음 |

`exp`는 사실상 필수다. 없으면 토큰이 영원히 유효해서 한 번 탈취되면 끝이다. `nbf`는
특정 시각부터 유효하게 하는 예약 발급에 쓴다. 라이브러리는 보통 이 시간 클레임들을
자동으로 검사한다.

```python
import jwt, datetime

secret = "DUMMY-SECRET-DO-NOT-USE"  # 실제로는 환경변수/시크릿 매니저에서
# utcnow()는 tz 정보 없는 naive datetime을 돌려주고 3.12에서 deprecated됐다.
# 시간 클레임은 tz-aware로 만드는 편이 안전하다.
now = datetime.datetime.now(datetime.timezone.utc)

token = jwt.encode(
    {"sub": "1234", "role": "user",
     "iat": now, "exp": now + datetime.timedelta(minutes=15)},
    secret, algorithm="HS256",
)

# 검증: 서명 불일치·만료면 예외가 난다. algorithms를 반드시 명시한다.
decoded = jwt.decode(token, secret, algorithms=["HS256"])
```

## 근본 문제: 발급한 토큰을 어떻게 무효화하나

세션은 서버 저장소에서 지우면 즉시 로그아웃이지만, JWT는 서버가 아무것도 들고 있지 않다.
이미 발급해 클라이언트 손에 있는 토큰은 `exp`가 올 때까지 서명이 유효한 채로 살아 있다.
비밀번호를 바꿔도, 계정을 정지시켜도 그 토큰은 만료 전까지 계속 통과한다. 무상태의
정확한 대가다. 현실적인 대응은 몇 가지를 조합한다.

**access + refresh 분리.** access token은 수명을 짧게(분 단위) 둔다. 탈취돼도 금방 만료되니
피해 창이 좁다. 대신 자주 만료되므로 수명이 긴(일 단위) refresh token으로 재발급받는다.
refresh token은 서버가 저장·추적하므로 여기서 폐기가 가능하다. 로그아웃이나 탈취 대응은
결국 refresh token을 서버 저장소에서 무효화하는 것으로 이뤄진다. access의 무상태 이점은
살리되, 통제가 필요한 부분만 상태를 도로 들이는 절충이다.

**블랙리스트.** 강제 로그아웃해야 할 access token의 식별자(`jti`)를 만료 시점까지만
저장소에 담아 두고 검증 시 대조한다. 완전한 무상태는 아니게 되지만, 목록이 만료와 함께
비워지므로 세션 저장소보다는 가볍다.

**토큰 버전.** 사용자 레코드에 `token_version` 정수를 두고 토큰 payload에도 넣는다.
비밀번호 변경 등 전면 무효화 이벤트가 나면 DB의 버전을 올린다. 검증 시 토큰의 버전과
DB 버전이 다르면 거부한다. 사용자당 정수 하나만 조회하면 되니 부담이 작다.

순수한 무상태 JWT로는 즉시 무효화가 안 된다. 어디까지 무상태를 포기할지를 정하는 게
설계의 핵심이다.

## 보안 함정

JWT는 개념보다 운영에서 실수하기 쉽다.

**`alg:none` 공격.** 헤더의 `alg`를 `none`으로 바꾸고 서명을 통째로 비운 토큰을 보내는
고전적 공격이다. 옛 라이브러리 중엔 `alg`를 토큰이 시키는 대로 믿고 "서명 없음"을
통과시키는 것들이 있었다. 방어는 검증 시 서버가 기대하는 알고리즘을 고정하는 것이다. 위
코드의 `jwt.decode(..., algorithms=["HS256"])`처럼 허용 목록을 못 박는 게 이 방어다. 관련
변종으로, RS256으로 발급했는데 검증을 HS256으로 열어 두면 공격자가 공개키를 HMAC
비밀키로 악용하는 알고리즘 혼동(algorithm confusion)도 있다.

**약한 시크릿.** HS256의 비밀키가 `secret`이나 짧은 문자열이면 오프라인 무차별 대입으로
털린다. 키가 털리면 공격자가 원하는 payload로 유효한 토큰을 마음껏 찍어낸다. 충분히 길고
무작위한 값을 쓰고, 코드가 아니라 환경변수나 시크릿 매니저에서 주입한다.

**payload에 비밀 담기.** payload는 평문이다. 여기 개인정보나 비밀을 넣는 순간 토큰을 가진
누구에게나 노출된다. 되돌려 써야 하는 비밀값을 저장해야 한다면 JWT가 아니라 대칭
암호화의 영역이다. 이 주제는 [Fernet 정리](https://rlckdwkd55.github.io/posts/fernet-encryption/)에서 따로 다룬다.

**저장 위치.** 브라우저에서 토큰을 어디 둘지도 트레이드오프다. `localStorage`는
자바스크립트로 읽혀 XSS에 취약하고, 쿠키는 자동 전송돼 CSRF에 노출된다. 쿠키를 쓴다면
`HttpOnly`(JS 접근 차단)·`Secure`(HTTPS 전용)·`SameSite`로 방어를 겹쳐야 한다.

## 인증(authn)과 인가(authz)는 다른 층이다

**인증(authentication)**은 "누구냐"를 확인하는 일이고, **인가(authorization)**는 "그래서 이
작업을 할 수 있느냐"를 판단하는 일이다. JWT는 기본적으로 인증 도구다. 서명 검증으로
"이 요청은 사용자 1234가 보낸 게 맞다"까지 말해 준다.

토큰 payload에 `role`이나 권한을 넣어 인가에 활용할 수는 있지만, 그것은 JWT가 인가를 해
주는 게 아니라 인가 판단에 쓸 정보를 실어 나르는 것뿐이다. "이 역할이 이 메뉴의 쓰기를
할 수 있는가" 같은 판단은 별도의 권한 체계가 맡는다. 이 부분은
[RBAC 정리](https://rlckdwkd55.github.io/posts/rbac/)에서 따로 다룬다. Spring 진영에서는
필터 체인이 인증과 인가를 나눠 처리하는데, 그 구조는
[Spring Security 기본 구조](https://rlckdwkd55.github.io/posts/spring-security/)에 정리돼 있다.
인증과 인가를 한 덩어리로 뭉뚱그리면 "로그인만 됐으면 다 되는" 허술한 구조가 나오기 쉽다.

---

정리하면 JWT는 서명된 토큰으로 하는 무상태 인증 방식이다. 구조는
`header.payload.signature`이고, payload는 인코딩일 뿐 암호화가 아니므로 비밀을 담지 않는다.
HS256은 단일 서비스, RS256은 발급자와 검증자가 분리될 때 쓴다. 무상태의 대가인 즉시
무효화 문제는 access/refresh 분리, 블랙리스트, 토큰 버전으로 절충하고, 함정 대부분은
운영에서 나므로 알고리즘 고정·강한 시크릿·payload 비밀 금지·저장 위치 관리를 챙긴다.
