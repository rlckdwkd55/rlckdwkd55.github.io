## 검색은 되지만 집계가 안 되는 로그

로그는 보통 사람이 읽기 좋은 **한 줄 문자열**이다.

```text
2025-12-24 10:15:32 INFO  search Request - index=product keyword=노트북 took=42
```

이대로 Elasticsearch에 넣으면 `message` 필드 하나에 문자열 전체가 담긴다. "노트북"으로
전문 검색은 되지만, **keyword별 상위 N**이나 **index별 트래픽** 같은 집계는 되지 않는다.
집계는 필드 단위로 이뤄지는데, 정작 `keyword`·`index`가 별도 필드로 존재하지 않기
때문이다. (색인은 되는데 집계에 왜 필드가 필요한지는
[역색인 글](https://rlckdwkd55.github.io/posts/elasticsearch-inverted-index/)에서 다룬다.)

**Logstash**는 이 지점을 메운다. 원시 문자열에서 필드를 뽑아 **구조화된 JSON**으로 바꿔
Elasticsearch에 넣어 주는, ELK의 "수집·변환" 담당이다.

## input → filter → output

Logstash 파이프라인은 이벤트가 지나가는 세 단계로 이뤄진다.

```text
input  { ... }   # 어디서 받을까 (beats, file, kafka ...)
filter { ... }   # 어떻게 가공할까 (grok, date, mutate, geoip, json ...)
output { ... }   # 어디로 보낼까 (elasticsearch, stdout, kafka ...)
```

- **input** — 데이터 소스. Filebeat에서 받는 `beats`, 파일을 직접 tail하는 `file`,
  버퍼 역할을 하는 `kafka` 등이 있다.
- **filter** — 핵심 가공 단계. 파싱·형변환·필드 조작·보강(enrich)이 여기서 일어난다.
- **output** — 목적지. 보통 Elasticsearch 인덱스지만, 디버깅용 `stdout`도 자주 쓴다.

한 줄의 로그가 들어와 하나의 **이벤트(event)** 가 되고, filter를 통과하며 필드가 붙거나
바뀌고, output으로 나간다. 아래는 앞의 검색 로그를 처리하는 파이프라인 전체 예시다.

```conf
input {
  beats {
    port => 5044
  }
}

filter {
  grok {
    match => {
      "message" => "%{TIMESTAMP_ISO8601:ts} %{LOGLEVEL:level}\s+search Request - index=%{DATA:index} keyword=%{GREEDYDATA:keyword} took=%{NUMBER:took_ms:int}"
    }
  }

  date {
    match    => ["ts", "yyyy-MM-dd HH:mm:ss"]
    timezone => "Asia/Seoul"
    target   => "@timestamp"
  }

  mutate {
    lowercase    => ["level"]
    remove_field => ["message", "ts"]
  }
}

output {
  elasticsearch {
    hosts => ["http://es:9200"]
    index => "search-logs-%{+YYYY.MM.dd}"
  }
}
```

## grok — 정규식에 이름을 붙여 필드로 분해

`filter`에서 가장 많이 쓰는 것이 **grok**이다. 정규식을 그대로 쓰는 대신, 자주 쓰는
패턴에 이름을 붙여 둔 것을 조합한다. `%{패턴이름:필드이름}` 꼴로 쓴다.

- `%{TIMESTAMP_ISO8601:ts}` — ISO 8601 시각을 잡아 `ts` 필드에 담는다.
- `%{LOGLEVEL:level}` — `INFO`/`WARN`/`ERROR` 같은 레벨.
- `%{NUMBER:took_ms:int}` — 숫자를 잡되 `:int`로 **정수 형변환**까지 한다.

위 파이프라인을 앞의 로그에 적용하면 이렇게 구조화된다.

```json
{
  "level": "info",
  "index": "product",
  "keyword": "노트북",
  "took_ms": 42,
  "@timestamp": "2025-12-24T01:15:32.000Z"
}
```

`keyword`로 집계하면 **인기검색어**가, `index`로 집계하면 인덱스별 트래픽이,
`took_ms`로 집계하면 응답시간 분포가 나온다. 검색만 되던 로그가 분석 대상이 된 것이다.

grok 내부는 Oniguruma 정규식 엔진이다. 편한 대신 정규식의 함정도 그대로 따라오는데,
가장 흔한 것이 **패턴 불일치**다.

- 로그 포맷이 조금만 바뀌어도(공백 하나, 필드 순서) grok이 실패하고 이벤트에
  `_grokparsefailure` 태그가 붙는다. 태그만 쌓이고 필드는 안 뽑히는 상태다.
- 그래서 **로그 포맷과 grok 패턴을 한 세트로 관리**해야 한다. 애플리케이션 로그 포맷을
  바꾸는 변경에는 파이프라인 패턴 수정도 함께 들어가야 한다.

## date와 mutate — 시각을 맞추고 필드를 정리

**date 필터**가 없으면 `@timestamp`는 Logstash가 로그를 **받은 시각**이 된다. 수집이
밀리거나 재처리를 하면 실제 발생 시각과 어긋나 시계열이 뒤틀린다. 그래서 로그 안의
시각 문자열(`ts`)을 파싱해 `@timestamp`로 덮어써야 한다. 이때 **타임존**을 명시하지
않으면 UTC로 해석돼 9시간이 밀린다(예시의 `Asia/Seoul`).

**mutate 필터**는 필드 뒷정리 담당이다. 자주 쓰는 조작은 다음과 같다.

| 옵션 | 하는 일 |
|---|---|
| `rename` | 필드 이름 변경 (`{"took" => "took_ms"}`) |
| `convert` | 형변환 (`{"took_ms" => "integer"}`) |
| `lowercase` / `uppercase` | 대소문자 정규화 |
| `gsub` | 정규식 치환으로 값 정리 |
| `remove_field` | 불필요한 필드 삭제 |

예시에서 `remove_field`로 `message`(원본 문자열)와 `ts`(중간 산물)를 지운 이유는 저장
용량이다. grok으로 필드를 다 뽑았으면 원문은 대개 필요 없고, 그대로 두면 인덱스가 두 배로
커진다. 이 외에 IP를 위경도로 바꾸는 `geoip`, JSON 문자열 필드를 다시 구조화하는 `json`
필터도 상황에 맞게 조합한다.

일자별 인덱스(`search-logs-%{+YYYY.MM.dd}`)로 쌓으면, 날짜로 인덱스가 쪼개져 있어 오래된
로그를 인덱스 통째로 삭제하는 수명주기(ILM) 관리가 쉽다.

## 영속 큐와 배압 — 뒤가 막혀도 로그를 흘리지 않기

input과 filter 사이에는 **큐(queue)** 가 있다. 기본은 메모리 큐라 Logstash가 죽으면 그 안의
이벤트는 사라진다. Elasticsearch가 잠깐 느려지거나 재시작하는 순간 유실이 날 수 있는 구조다.

이걸 막는 게 **영속 큐(persistent queue)** 다. `queue.type: persisted`로 켜면 큐를 디스크에
쓴다. 그 덕에 두 가지를 얻는다.

- **내구성** — Logstash가 재시작돼도 처리 중이던 이벤트가 남아 이어서 처리된다.
- **버스트 흡수** — output이 순간적으로 느려도 디스크 큐가 버퍼가 되어 준다.

큐가 가득 차면 **배압(backpressure)** 이 발생한다. Logstash가 input을 잠시 멈추고, 그 신호가
앞단(Filebeat)까지 거슬러 올라가 수집 속도를 늦춘다. 받는 쪽을 밀어붙이지 않는 이 흐름 제어는
Filebeat 쪽에서도 동작하며, 그 내용은
[Filebeat 글](https://rlckdwkd55.github.io/posts/filebeat/)에서 다룬다.

## grok 비용과 역할 분담

Logstash는 JVM 위에서 돈다. 그래서 가볍지 않고, 특히 **grok가 비싸다.** 정규식 백트래킹
때문인데, 매칭이 실패하는 경우가 최악이다. 엔진이 온갖 경우의 수를 시도하다 포기하기
때문이다. `GREEDYDATA`·`DATA`를 남발하면 이 비용이 커진다. 완화 방법은 다음과 같다.

- **패턴을 앵커링**한다(`^ ... $`). 불필요한 탐색 범위를 줄인다.
- 포맷이 **구분자로 고정**돼 있으면 grok 대신 **dissect** 필터를 쓴다. 정규식이 아니라
  위치 기반 분해라 훨씬 싸다.
- filter+output을 병렬로 돌리는 `pipeline.workers`, 배치 크기 `pipeline.batch.size`를
  장비에 맞게 조정한다.

여기서 **역할 분담**이 나온다. 무엇을 어디서 가공할지의 문제다.

| 방식 | 성격 | 언제 |
|---|---|---|
| **Beats(Filebeat)** | 초경량 수집, 가공 거의 없음 | 엣지에서 로그를 실어 나르기만 |
| **Logstash** | 무거운 변환(grok, enrich, 여러 output) | 본격적인 파싱·보강이 필요할 때 |
| **ES ingest pipeline** | ES 노드 안에서 간단 파싱 | Logstash 없이 가벼운 grok/변환만 |

핵심은 **수집은 가볍게 엣지에서, 무거운 가공은 중앙에서** 나눈다는 것이다. 단순 수집이라면
Filebeat → Elasticsearch(ingest pipeline)로 Logstash를 생략할 수도 있다. 반대로 grok
파싱·필드 보강·여러 목적지 분기가 필요해지는 순간 Logstash가 제값을 한다. 검색 로그처럼
grok 파싱이 핵심인 경우가 Logstash를 거치는 쪽에 해당한다.

정리하면, Logstash는 **input → filter → output** 파이프라인으로 비정형 로그를 구조화한다.
grok로 필드를 뽑고, date로 `@timestamp`를 실제 발생 시각에 맞추고, mutate로 필드를
정리하면 검색만 되던 로그가 집계 대상이 된다. 영속 큐와 배압이 유실 없는 흐름 제어를 맡고,
비싼 grok는 앵커링·dissect로 완화하며, 수집(Beats)과 가공(Logstash)의 역할을 나누는 것이
설계의 축이다. 이렇게 구조화한 로그를 눈으로 보는 단계는
[Kibana 글](https://rlckdwkd55.github.io/posts/kibana/)에서 이어 간다.
