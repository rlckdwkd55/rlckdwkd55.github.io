## Alembic이 푸는 문제

DB 스키마를 손으로 변경하면 재현이 어렵다. `ALTER TABLE ...` 을 로컬에서 실행하고 같은
SQL을 운영에 다시 돌리는 방식은 어느 환경에 무엇이 적용됐는지를 사람의 기억에 의존하게
만들고, 로컬엔 있고 스테이징엔 빠진 인덱스나 실행 순서가 달라 어긋난 스키마 같은 문제를
낳는다.

**Alembic**은 스키마 변경을 **Git에 커밋되는 파일(리비전)** 로 남긴다. 그러면 "이 커밋
시점의 코드는 이 스키마와 짝"이라는 대응이 성립하고, 어느 환경이든 `alembic upgrade head`
한 번으로 같은 상태에 도달한다. 애플리케이션 코드처럼 DB 스키마에 버전 관리를 붙이는
도구다.

## 리비전 — 스키마 변경 이력의 단위

Alembic은 **리비전(revision)** 을 단위로 동작한다. 리비전 하나는 스키마 변경 한 단계이고,
각 파일은 고유 ID와 **`down_revision`**(바로 이전 리비전의 ID)을 가진다. 이 `down_revision`
포인터 때문에 전체 리비전은 부모를 가리키며 이어지는 **체인(사실상 DAG)** 을 이룬다.

```text
(base) → a1b2 → c3d4 → e5f6 (head)
                         ▲ 가장 최신 = head
```

- **base** — 아무것도 적용되지 않은 시작점(`down_revision = None`).
- **head** — 체인의 끝, 즉 최신 리비전. 보통 `alembic upgrade head` 로 여기까지 올린다.
- **`alembic_version` 테이블** — DB 안에 자동 생성되며, 지금 이 DB가 어느 리비전까지
  적용됐는지를 한 줄로 저장한다. Alembic은 이 값과 리비전 체인을 비교해 어디서부터
  어디까지 실행할지를 계산한다.

`down_revision`이 정수가 아니라 **부모 리비전의 ID**라는 점이 핵심이다. 순서가 파일명이나
날짜가 아니라 이 포인터로 결정되므로 브랜치가 갈리거나 머지가 생겨도 순서를 추적할 수 있다.

## upgrade / downgrade

리비전 파일의 구조는 단순하다. 앞으로 적용하는 `upgrade()`, 되돌리는 `downgrade()`,
상단 메타데이터가 전부다.

```python
# versions/c3d4_add_user_is_active.py
revision = "c3d4"
down_revision = "a1b2"      # 이 리비전의 부모
branch_labels = None
depends_on = None

from alembic import op
import sqlalchemy as sa


def upgrade() -> None:
    op.add_column(
        "users",
        sa.Column("is_active", sa.Boolean(), nullable=False,
                  server_default=sa.true()),
    )
    op.create_index("ix_users_is_active", "users", ["is_active"])


def downgrade() -> None:
    op.drop_index("ix_users_is_active", table_name="users")
    op.drop_column("users", "is_active")
```

`op` 객체는 `create_table`, `add_column`, `alter_column`, `create_index`,
`execute`(생 SQL) 같은 DDL 연산을 DB 방언에 맞게 생성한다. 규율로 삼을 것은
**`downgrade()`는 `upgrade()`의 정확한 역순**이어야 한다는 점이다. 역순이 어긋나면 롤백이
필요한 순간에 downgrade가 깨진다. 자주 쓰는 명령은 다음과 같다.

```bash
alembic upgrade head      # 최신까지 전부 적용
alembic upgrade +1        # 한 단계만 전진
alembic downgrade -1      # 한 단계 되돌리기
alembic downgrade base    # 전부 되돌리기
alembic current           # 지금 DB가 어느 리비전인지
alembic history --verbose # 리비전 체인 전체 보기
```

## autogenerate의 원리와 한계

가장 편한 기능이자 가장 조심해야 하는 기능이 `--autogenerate` 다.

```bash
alembic revision --autogenerate -m "add user.is_active"
```

Alembic은 **SQLAlchemy 모델의 메타데이터(`Base.metadata`)** 가 기대하는 스키마와 **실제
DB를 인스펙션(inspect)한 현재 스키마**를 비교하고, 그 차이(diff)를 `op.*` 호출로 번역해
리비전 초안을 만든다. 문제는 이 비교가 **완전하지 않다**는 점이다. 대표적인 한계는
다음과 같다.

- **컬럼 이름 변경을 못 잡는다.** `username` 을 `login_id` 로 바꾸면 이름 변경이 아니라
  **`drop_column("username")` + `add_column("login_id")`** 로 생성해 **기존 데이터가 전부
  날아간다.** 손으로 `op.alter_column("users", "username", new_column_name="login_id")` 로
  고쳐야 한다.
- **서버 기본값 변경은 기본적으로 무시된다.** `compare_server_default` 옵션이 **기본값
  `False`** 라, `env.py` 에서 명시적으로 켜야 diff에 잡힌다. 타입 비교(`compare_type`)는
  Alembic **1.12.0부터 기본값이 `True`로 바뀌었으니**, 그보다 낮은 버전을 쓴다면 이쪽도
  직접 켜야 한다.
- **이름 없는 제약·인덱스는 놓치기 쉽다.** 이름 규칙(naming convention)이 없으면 대상을
  특정하지 못해 diff가 불안정해진다.
- **테이블 밖 객체는 못 본다.** `CHECK` 표현식, 트리거, 뷰, 확장(extension)은 모델
  메타데이터에 없으므로 `op.execute()` 로 직접 써야 한다.

따라서 **autogenerate가 만든 파일은 초안일 뿐, 반드시 사람이 검토한다.** 리비전 생성
직후 diff를 열어 rename이 drop+add로 둔갑하지 않았는지, 의도한 인덱스·제약이 다
들어갔는지, `downgrade()`가 역순으로 맞는지를 확인한다.

## env.py — 모델과 DB를 잇는 접점

autogenerate가 동작하려면 `env.py` 가 **어떤 메타데이터를 기준으로 비교할지**를 알아야
한다. 그래서 이 파일에서 `target_metadata` 를 모델의 `Base.metadata` 로 연결하고, 비교
옵션도 함께 켠다.

```python
# alembic/env.py 일부
from myapp.models import Base   # 모든 모델이 등록된 declarative Base

target_metadata = Base.metadata

def do_run_migrations(connection):
    context.configure(
        connection=connection,
        target_metadata=target_metadata,
        compare_type=True,             # 타입 변경도 감지
        compare_server_default=True,   # 서버 기본값 변경도 감지
    )
    with context.begin_transaction():
        context.run_migrations()
```

흔한 함정은 **모델을 import하지 않아 메타데이터가 비어 있는 경우**다. 모델 파일이 어디서도
import되지 않으면 `Base.metadata` 에 등록되지 않고, autogenerate는 그 테이블을 "DB엔 있는데
모델엔 없다"고 오해해 **`drop_table`** 을 제안한다. 모델을 모아 import하는 지점(예:
`models/__init__.py`)을 두는 이유다.

**async 엔진을 쓸 때**는 한 겹 더 조심한다. Alembic의 마이그레이션 실행부는 원래 동기
코드라, `create_async_engine` 으로 만든 엔진을 그대로 넘길 수 없다. 비동기 커넥션 위에서
동기 마이그레이션 함수를 돌리려면 `connection.run_sync(...)` 로 감싸야 한다.

```python
import asyncio
from sqlalchemy.ext.asyncio import async_engine_from_config

async def run_async_migrations():
    engine = async_engine_from_config(
        config.get_section(config.config_ini_section),
        prefix="sqlalchemy.",
    )
    async with engine.connect() as connection:
        await connection.run_sync(do_run_migrations)   # 동기 함수를 async 위에서
    await engine.dispose()

asyncio.run(run_async_migrations())
```

`alembic init -t async` 로 시작하면 이 형태의 `env.py` 템플릿이 자동으로 깔리므로, async
앱이라면 처음부터 async 템플릿으로 시작하는 편이 낫다. 비동기 엔진·세션 자체의 동작은
[SQLAlchemy 비동기 글](https://rlckdwkd55.github.io/posts/sqlalchemy-async/)에 따로 정리했다.

## 브랜치와 머지 — head가 갈릴 때

같은 부모 리비전에서 두 사람이 각자 `alembic revision` 을 만들면, 두 리비전이 **같은
`down_revision`** 을 가리키게 된다. 그 결과 head가 두 개로 갈라지고(**multiple heads**),
이 상태에서 `alembic upgrade head` 를 치면 head가 여러 개라 목적지를 정할 수 없다는
에러가 난다.

```bash
alembic heads        # 갈라진 head 두 개가 보인다
alembic merge -m "merge feature-a and feature-b" heads
```

`merge` 리비전은 특별하다. `down_revision` 이 **튜플**(여러 부모)이 되어 두 갈래를 다시
하나로 합친다. 대개 upgrade/downgrade 본문은 비어 있고 순서를 정리하는 역할만 한다.
Git의 머지 커밋과 같은 개념이다. 운영 배포 전에는 `alembic heads` 로 head가 하나인지
확인한다.

## 운영 배포에서 조심할 것

로컬과 달리 운영 DB에서는 다음 원칙이 중요하다.

- **되돌리기 어려운 변경을 함부로 넣지 않는다.** 컬럼을 `drop` 하면 downgrade로 컬럼은
  되살려도 **데이터는 못 살린다.** 파괴적 변경은 배포 전략과 묶어 계획한다.
- **무중단이 필요하면 확장-수축(expand-contract)으로 나눈다.** 컬럼 rename이라면 ① 새 컬럼
  추가(expand) → ② 두 컬럼을 모두 쓰는 앱 배포와 데이터 백필 → ③ 옛 컬럼 제거(contract).
  각 단계를 별도 리비전·별도 배포로 쪼개 앱과 스키마가 항상 호환되게 유지한다.
- **스키마 변경과 데이터 마이그레이션을 분리한다.** 수백만 행 `UPDATE` 같은 대용량 이관을
  `upgrade()` 안에 넣으면 **테이블 잠금**으로 배포가 멈춘다. 무거운 백필은 별도
  배치·스크립트로 뺀다.
- **잠금과 인덱스 생성을 의식한다.** PostgreSQL에서 큰 테이블에 인덱스를 만들면 기본
  방식은 쓰기를 막는다. `CREATE INDEX CONCURRENTLY` 로 피할 수 있지만 트랜잭션 안에서
  못 돌리므로 Alembic 트랜잭션 설정을 조정해야 한다.
- **리비전도 코드 리뷰 대상이다.** 운영에서 도는 `upgrade()` 는 PR diff로 확인받고,
  autogenerate 초안을 검토 없이 머지하지 않는다.

배포 직전 `alembic upgrade head` 대신 `alembic upgrade head --sql` 로 **실행될 SQL을 먼저
뽑아 확인**하는 것도 안전장치가 된다.
