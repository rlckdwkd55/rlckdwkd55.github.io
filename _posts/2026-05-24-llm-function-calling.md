LLM은 학습 시점에 갇힌 텍스트 생성기다. 스스로 DB를 조회하거나 사내 API를 부르지
못한다. 그런데 실무에서 필요한 것은 대부분 "질문에 답하기"가 아니라 "무언가를 조회하고,
계산하고, 처리하기"다. 이 간극을 메우는 것이 **Function Calling(Tool Calling)** 이다.

핵심은 한 문장으로 정리된다. **모델은 함수를 실행하지 않는다. "이 함수를 이 인자로 불러
달라"는 구조화된 요청을 만들 뿐이다.** 이 전제를 오해하면 실행과 권한의 경계를 잘못 긋게
되므로 먼저 못 박아 둔다.

## 왜 필요한가

LLM 단독으로는 세 가지를 못 한다.

- **실시간 데이터** — 환율, 재고, 오늘 날씨처럼 학습 이후에 바뀌는 값.
- **사설 데이터** — 서비스의 주문 내역, 사용자 설정처럼 모델이 본 적 없는 정보.
- **행동(side effect)** — 메일 발송, 결제, 레코드 생성처럼 세상을 바꾸는 작업.

Function Calling은 이 세 가지를 "도구(tool)"라는 인터페이스로 모델에 노출한다. 모델은
대화 맥락을 보고 "지금은 검색 도구가 필요하다"를 스스로 판단하고 필요한 인자를 채워 호출을
요청한다. 실행과 권한은 여전히 애플리케이션이 쥔다는 점이 중요하다.

## 동작 흐름 — 실행이 아니라 요청의 왕복

전체 그림은 앱과 모델 사이의 왕복이다.

1. 앱이 모델에게 **사용 가능한 도구 목록(스키마)** 을 함께 넘긴다.
2. 모델이 필요하다고 판단하면 텍스트 대신 **"함수명 + 인자(JSON)"** 형태의 tool call을 반환한다.
3. 앱이 그 함수를 **실제로 실행**한다. 여기서 권한·검증이 개입한다.
4. 실행 결과를 대화에 도구 결과로 붙여 **다시 모델에 넣는다.**
5. 모델이 그 결과를 근거로 최종 답변을 만든다.

```text
[사용자] "서울 날씨 알려줘"
   │
   ▼
[모델] tool_call: get_weather(city="서울")   ← 실행이 아니라 "요청"
   │
   ▼
[앱]   get_weather("서울") 실행 → { "temp_c": 28, "sky": "맑음" }
   │  (도구 결과를 대화에 주입해 다시 호출)
   ▼
[모델] "서울은 현재 28도로 맑습니다."
```

이 왕복 구조가 곧 **에이전트 루프의 기반**이다. 4→5에서 모델이 또 다른 도구 호출을
요청하면 앱은 다시 3으로 돌아간다. "모델이 더 이상 도구를 부르지 않을 때까지 반복"하는 이
루프는 직접 짤 수도 있지만, 상태·분기가 복잡해지면
[LangGraph](https://rlckdwkd55.github.io/posts/langgraph/)로 그래프를 그려 관리하는
편이 낫다.

## 도구 스키마 — 모델이 읽는 유일한 설명서

도구는 **이름 + 설명 + 파라미터 스키마(JSON Schema)** 로 정의한다. 모델은 이 스키마와
설명만 보고 "언제, 어떤 인자로 부를지"를 결정하므로, 설명이 곧 성능이다.

```json
{
  "name": "get_order_status",
  "description": "주문 번호로 현재 배송 상태를 조회한다. 사용자가 '내 주문 어디쯤이야' 류의 질문을 할 때 호출한다.",
  "parameters": {
    "type": "object",
    "properties": {
      "order_id": {
        "type": "string",
        "description": "조회할 주문 번호. 예: 'ORD-20260608-001'"
      }
    },
    "required": ["order_id"]
  }
}
```

설명을 `"주문 조회"` 한 줄로만 두면 모델이 엉뚱한 타이밍에 도구를 부르거나 아예 부르지
않는다. **"무엇을 하는가"만이 아니라 "언제 불러야 하는가"까지** 써 넣으면 호출 정확도가
눈에 띄게 오른다.

## 호출을 통제하는 장치들

### tool_choice — 자동이냐 강제냐

- **auto** — 모델이 도구를 쓸지 말지 스스로 결정한다. 기본값이자 대화형 챗봇의 표준.
- **강제(특정 도구/아무 도구나)** — 반드시 도구를 부르게 한다. "무조건 검색부터 하고 답해" 같은 파이프라인에서 쓴다.
- **none** — 도구를 못 쓰게 막는다. 순수 텍스트 답변이 필요한 구간.

### 병렬 도구 호출

한 번의 응답에서 모델이 여러 tool call을 동시에 요청할 수 있다. "서울과 부산 날씨"를
물으면 `get_weather("서울")`, `get_weather("부산")` 두 호출이 한 응답에 담긴다. 이때 앱은
각각 실행한 뒤 **모든 결과를 빠짐없이 모아** 다음 요청에 넣어야 한다. 하나라도 빠뜨리면
모델이 삐지는 게 아니라 **대화 이력의 짝이 맞지 않아 API가 요청 자체를 거부한다.**
tool call 하나에는 그에 대응하는 결과 메시지 하나가 반드시 따라붙어야 한다는 게 프로토콜의
계약이고, OpenAI 계열은 이걸 어기면 400을 돌려준다.

## 가장 큰 함정 — 모델은 인자를 틀리게, 때로 환각으로 채운다

모델이 반환하는 tool call은 **JSON처럼 생겼을 뿐, 스키마를 항상 지킨다는 보장이 없다.**
자주 나타나는 유형은 이렇다.

- `required` 인자를 빠뜨린다.
- 타입이 어긋난다 (수량 `2`를 `"두 개"`로).
- 대화에 없던 값을 그럴듯하게 지어낸다 (**인자 환각**).

그래서 **도구 실행 직전에 스키마 검증을 반드시 통과시키는** 방어선을 둔다. 검증에는
[Pydantic](https://rlckdwkd55.github.io/posts/pydantic/)을 쓴다. 모델이 준 인자를 모델
클래스로 파싱하고, 실패하면 실행하지 않고 **에러를 도구 결과로 되돌려 준다.**

```python
from pydantic import BaseModel, ValidationError

class GetOrderStatusArgs(BaseModel):
    order_id: str

def run_tool(tool_call) -> dict:
    # 1) 스키마 검증 — 실패하면 실행하지 않고 에러를 모델에 반환
    try:
        args = GetOrderStatusArgs.model_validate(tool_call.arguments)
    except ValidationError as e:
        return {"is_error": True, "content": f"인자 오류: {e.errors()}"}

    # 2) 검증을 통과한 값만 실제 함수로 넘긴다
    status = order_repository.find_status(args.order_id)
    if status is None:
        return {"is_error": True, "content": f"주문 없음: {args.order_id}"}
    return {"content": status}
```

에러를 예외로 던져 흐름을 끊는 대신 **도구 결과로 돌려주는 게 핵심**이다. 그러면 모델은
"인자가 틀렸구나"를 읽고 스스로 재시도하거나 사용자에게 되묻는다. 이 자기수정 루프가
없으면 잘못된 호출 한 번에 전체 대화가 무너진다.

### 실행 권한과 부작용은 별개 문제다

검증을 통과했다고 실행이 안전한 것은 아니다. 조회(읽기)는 몰라도 **메일 발송·삭제·결제처럼
되돌리기 어려운 작업**은 모델의 판단만 믿고 자동 실행하면 안 된다. 부작용이 있는 도구는
사람의 승인 단계를 한 겹 두거나 실행 계정의 권한 자체를 최소로 조인다. 모델이 아무리
그럴듯하게 호출해도 권한이 없으면 사고로 이어지지 않는다.

## 구조화 출력과의 관계

Function Calling은 결과적으로 **"모델이 자유 텍스트 대신 정해진 JSON을 뱉게 만드는"
기법**이기도 하다. 실제로 도구를 실행할 생각이 없어도 스키마에 맞는 인자를 받는 것 자체가
목적일 때가 있다. 예를 들어 사용자 문장에서 `{name, email, plan}`을 추출하려면 그런
필드를 가진 도구를 하나 정의하고 모델이 그 도구를 "호출"하도록 강제하면 된다.

요즘은 이 용도를 위해 별도의 **구조화 출력(structured output)** 기능을 제공하는 API가
많다. 스키마를 응답 형식으로 직접 강제하는 방식이라, "행동"이 목적이면 tool calling을,
"정해진 형태의 데이터 추출"이 목적이면 구조화 출력을 쓰는 식으로 구분한다.

## 실무 변수 — 모델·서빙 엔진별 호환성

표준이 하나가 아니라는 점도 실무의 큰 변수다. 도구를 정의하는 형식과 모델이 반환한 tool
call을 파싱하는 방식이 제공자마다 조금씩 다르다.

| 상황 | 자주 겪는 문제 | 대응 |
| --- | --- | --- |
| 오픈 모델을 [vLLM](https://rlckdwkd55.github.io/posts/vllm/)으로 서빙 | 모델에 맞는 tool-call 파서를 지정하지 않으면 호출이 파싱 안 됨 | 서빙 옵션에서 파서를 모델별로 명시 |
| "OpenAI 호환" 표방 엔드포인트 | 파라미터·형식 미세 차이로 호출 실패 | 실제 요청/응답을 로그로 찍어 스키마 대조 |
| 호환성·비용이 빠듯할 때 | tool calling 자체가 부담 | 일반 텍스트 생성 + 직접 파싱으로 우회 설계 |

특히 오픈 모델을 직접 서빙하는 환경에선 tool calling이 "된다/안 된다"가 파서 설정 하나에
갈리기도 한다. 새 모델을 붙일 때는 가장 단순한 도구 하나로 호출 왕복이 되는지부터 확인하고
넘어가는 편이 안전하다.

정리하면, Function Calling은 모델이 도구 호출을 구조화해 "요청"할 뿐 실행과 권한은 앱이
쥐는 구조다. 도구 스키마 제공 → tool_call 반환 → 앱 실행 → 결과 주입 → 최종 답변의 왕복이
에이전트 루프의 토대이며, 도구 설명은 "언제 부를지"까지 써야 호출 정확도가 오른다.
`tool_choice`로 자동·강제·차단을 통제하고 병렬 호출은 결과를 한 번에 모아 되돌린다. 모델은
인자를 틀리거나 환각하므로 Pydantic 검증과 에러 반환으로 자기수정 루프를 만들고, 부작용
있는 도구는 권한과 승인으로 방어한다. 정해진 형태의 데이터가 목적이면 구조화 출력이나 강제
tool call을 쓰고, 모델·엔진 호환성은 항상 먼저 검증한다.
