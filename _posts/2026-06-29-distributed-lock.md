애플리케이션이 한 대만 뜨던 시절에는 동시성이 프로세스 안의 문제였다. `threading.Lock` 하나면 스케줄러가
겹칠 일이 없었다. 그러나 인스턴스가 2대, 3대로 늘어나면 사정이 달라진다. 인스턴스마다 스케줄러가 살아 있으니
정해진 시각에 **모든 인스턴스가 동시에** 같은 작업을 시작하고, 같은 문서를 여러 번 색인하는 중복 실행이
발생한다.

이때 필요한 것이 **여러 프로세스가 공유하는 락**, 즉 분산 락이다. 분산 락은 만들기는 쉬운 반면 정확성을
보장하기는 까다롭다는 특징이 있다. 이 글은 그 간극을 정리한다.

---

## 단일 프로세스 락은 왜 소용없나

`threading.Lock`이나 `synchronized`가 동작하는 전제는 **모든 스레드가 같은 메모리 주소를 본다**는 것이다.
락 객체는 프로세스 힙 위의 상태값이고, 스레드들은 그 하나의 값을 놓고 경쟁한다.

인스턴스를 여러 대로 띄우면 이 전제가 깨진다. 인스턴스 A의 `Lock`과 인스턴스 B의 `Lock`은 **서로 다른
메모리에 있는 별개의 객체**다. A가 락을 잡아도 B의 락은 여전히 비어 있어, 둘 다 자기가 락을 잡았다고 믿으며
같은 작업에 진입한다.

따라서 락의 상태를 **프로세스 밖, 모두가 볼 수 있는 공유 저장소**로 옮겨야 한다. DB든 Redis든, 핵심은
작업의 소유권을 나타내는 표시를 **원자적으로** 남기고 확인하는 것이다.

```text
if 공유저장소에서_락_획득_성공:
    try:
        작업_수행()
    finally:
        락_해제()
else:
    pass  # 다른 인스턴스가 하는 중 → skip
```

관건은 락 획득이 원자적이어야 한다는 점이다. 두 인스턴스가 동시에 시도하면 **정확히 하나만** 성공해야 한다.
이 원자성을 어떻게 확보하느냐가 구현 방식을 가른다. 스케줄러 자체를 여러 인스턴스에서 돌리는 구성은
[스프링 스케줄러 정리](https://rlckdwkd55.github.io/posts/spring-scheduler/)에서 다룬다.

## DB 기반 — 이미 가진 인프라로

별도 인프라 없이 기존 RDB로 락을 만들 수 있다. 방법은 크게 세 가지다.

**1) 조건부 UPDATE로 소유권 획득**

락 상태를 담는 행을 하나 두고, 비었거나 만료됐을 때만 자기 이름으로 갱신한다.

```sql
UPDATE job_lock
SET locked_by = :me,
    lock_expires_at = :now + INTERVAL '30 minutes'
WHERE job = :job
  AND (locked_by IS NULL OR lock_expires_at < :now);
-- affected rows == 1 이면 락 획득, 0 이면 실패(다른 인스턴스가 보유 중)
```

`UPDATE ... WHERE`는 DB가 행 잠금으로 직렬화하므로, 여러 인스턴스가 동시에 이 쿼리를 던져도 **조건을
만족시킨 첫 번째 트랜잭션 하나만** affected rows 1을 받는다. 나머지는 0을 받고 물러난다. 실전에서 가장 많이
쓰이는 방식이며, 실제 스케줄러에 적용한 사례는
[분산 락 스케줄러 글](https://rlckdwkd55.github.io/posts/distributed-lock-scheduler/)에 따로 정리했다.

**2) `SELECT ... FOR UPDATE`(비관적 락)**

락 행을 읽으면서 잠가 두고, 트랜잭션이 끝날 때까지 다른 세션이 그 행을 못 건드리게 한다.

```sql
BEGIN;
SELECT * FROM job_lock WHERE job = :job FOR UPDATE;  -- 여기서 대기 발생
-- ... 소유권 판단 및 작업 ...
COMMIT;  -- 커밋/롤백 시점에 행 잠금 해제
```

락을 획득할 때까지 **대기**하는 시맨틱이다. 스케줄러처럼 이미 돌고 있으면 skip이 맞는 상황에는 대기가 오히려
독이라, `NOWAIT`이나 `SKIP LOCKED`을 붙여 즉시 실패시키는 편이 낫다. 락의 유효 범위가 **DB 트랜잭션
수명에 묶여** 커넥션이 끊기면 자동으로 풀린다는 점도 특징이다.

**3) 유니크 제약**

`INSERT`가 유니크 제약에 걸려 실패하는 성질을 락으로 쓴다. `INSERT INTO job_lock(job) VALUES (:job)`이
성공하면 락 획득, 중복 키 오류가 나면 이미 누군가 잡은 것이다. 간단하지만 만료 처리가 번거로워 보조적으로만
쓰인다.

DB 방식은 **트랜잭션과 함께 원자성이 딸려 오고** 기존 인프라로 끝난다는 장점이 있다. 단점은 락 획득이 곧 DB
부하라는 점, 그리고 초당 수천 건씩 다투는 고빈도 락에는 어울리지 않는다는 점이다.

## Redis 기반 — 빠르지만 미묘한

Redis는 인메모리라 락 경쟁이 빠르고, 단일 명령으로 원자적 획득이 된다.

```
SET lock:job "<owner-token>" NX EX 30
```

`NX`는 키가 없을 때만 세팅, `EX 30`은 30초 뒤 자동 만료를 뜻한다. 이 둘이 하나의 원자적 명령으로 묶인 것이
핵심이다. 해제할 때는 **자기가 잡은 락만** 지워야 하므로, value에 넣어 둔 토큰을 확인하고 지운다. 이 확인과
삭제도 원자적이어야 해서 Lua 스크립트로 처리한다.

```lua
-- KEYS[1]=lock:job, ARGV[1]=내 토큰
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

토큰 확인 없이 `DEL`만 하면 위험하다. 작업이 GC나 네트워크 지연으로 멈춘 사이 락이 TTL로 만료되고, 그 락을
**다른 인스턴스가 새로 잡았는데**, 뒤늦게 깨어난 쪽이 `DEL`로 **남의 락을 지워 버리는** 사고가 난다.

여러 Redis 노드에 걸쳐 정족수(quorum)로 락을 잡는 **Redlock** 알고리즘도 있다. N개 노드 중 과반에서 락을
얻으면 성공으로 보는 방식인데, 이것이 정말 안전한지를 두고 유명한 논쟁이 있었다(뒤에서 다룬다).

## TTL, 그리고 TTL이 만드는 새로운 위험

락에 만료 시간을 두는 것은 선택이 아니라 필수다. TTL이 없으면 락을 잡은 인스턴스가 크래시하거나 네트워크가
끊긴 순간 **락이 영원히 안 풀린다.** 아무도 그 작업을 다시 못 하는 데드락이다. 그래서 이 락을 30초만
임대(lease)한다는 개념이 들어온다.

문제는 여기서 시작된다. **TTL은 실제 작업 시간과 무관하게 흐른다.**

```text
t=0    인스턴스 A가 락 획득 (TTL 30초)
t=25   A가 STW GC 혹은 네트워크 지연으로 멈춤 (자기는 아직 락 보유 중이라 믿음)
t=30   TTL 만료 → 락 자동 해제
t=31   인스턴스 B가 같은 락 획득 → 작업 시작
t=35   A가 깨어남 → "나 아직 락 있지?" 하며 작업 계속
       => A와 B가 동시에 같은 작업을 수행 (락의 상호배제가 깨짐)
```

작업이 TTL보다 길어지는 순간, **두 노드가 동시에 락을 보유한다고 믿는** 창이 열린다. TTL을 길게 잡으면
크래시 후 복구가 느려지고, 짧게 잡으면 이 위험이 커진다. 어느 쪽도 근본 해결이 아니다. 락을 잡았다는 사실은
**어느 시점에 참이었다는 스냅숏일 뿐 지금 이 순간의 보장이 아니라는** 것이 분산 락의 본질적 한계다.

## 펜싱 토큰(fencing token)

이 문제의 정공법은 락 서비스가 아니라 **보호 대상 자원** 쪽에서 막는 것이다. 락을 내줄 때마다 **단조 증가하는
번호(펜싱 토큰)** 를 함께 발급하고, 자원에 쓸 때 그 번호를 같이 보낸다.

```text
A가 락 획득 → token=33
(A 멈춤, 락 만료)
B가 락 획득 → token=34
B가 자원에 쓰기 (token=34) → 저장소: "34 기록함"
A가 깨어나 자원에 쓰기 시도 (token=33) → 저장소: "이미 34를 봤다. 33은 거부"
```

자원(스토리지·DB)이 지금까지 본 것보다 작은 토큰을 거부하기만 하면, 뒤처진 노드의 쓰기를 확실히 막을 수
있다. **락만으로는 상호배제를 완벽히 보장할 수 없고, 자원 계층의 협조가 있어야 안전이 완성된다.** 다만 자원이
토큰 검사를 지원해야 하므로, 임의의 외부 API 호출 같은 부수효과에는 적용하기 어렵다.

## Redlock 논쟁

Martin Kleppmann은 Redlock이 정확성(correctness)이 필요한 용도에는 부적절하다고 비판했다. 요지는 이렇다.

- Redlock의 안전성은 **프로세스와 네트워크가 시간 안에 응답한다**는 타이밍 가정에 기댄다. 그러나 GC로 인한
  STW 정지, 페이지 폴트, 네트워크 지연은 그 가정을 언제든 깬다. 위의 TTL 시나리오가 그대로 재현된다.
- 이 문제는 노드 수를 늘려도(정족수를 써도) 사라지지 않는다. 진짜 해법은 **펜싱 토큰**인데, 그것은 Redlock
  바깥의 자원 계층 이야기다.

Redis 저자(antirez)는 클럭·타이밍 가정과 토큰의 역할에 대해 반박했고, 논쟁은 명쾌한 승패 없이 남았다. 다만
실무에 옮길 수 있는 결론은 분명하다.

## 정확성이냐 효율성이냐

분산 락을 쓸 때는 대상 작업이 어느 쪽인지부터 정해야 한다.

- **정확성이 생명인 곳**(중복되면 돈이 잘못 나가는 결제 등)에는 분산 락 하나에 정확성을 걸지 않는다. 펜싱
  토큰이나 자원 계층의 트랜잭션·유니크 제약으로 최종 방어선을 둔다.
- **효율성이 목적인 곳**(중복 실행이 낭비일 뿐 치명적이지 않은 스케줄러·배치)에는 분산 락으로 충분하다. 드물게
  겹치더라도 작업을 **멱등(idempotent)하게** 설계해 두면 결과가 틀어지지 않는다.

실무의 배치·스케줄러는 대부분 두 번째에 속하므로 **분산 락 + 멱등성**을 한 세트로 쓴다. 락으로 겹침을 드물게
줄이고, 멱등성으로 남은 드문 겹침을 무해하게 만드는 구성이다.
