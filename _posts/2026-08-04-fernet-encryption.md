복원해서 다시 써야 하는 비밀값을 저장할 때는 단방향 해시를 쓸 수 없다. 로그인 비밀번호라면
bcrypt로 해시하면 되지만, 외부 DB 접속 비밀번호처럼 **저장했다가 그대로 꺼내 접속에 써야
하는** 값은 다시 평문으로 복원돼야 한다. 필요한 것은 양방향으로 암·복호화되는 대칭키
암호화다. 파이썬 `cryptography` 라이브러리의 Fernet이 그 표준 레시피를 제공한다.

---

## 왜 직접 AES를 조립하지 않는가

AES 자체는 표준이고 안전한 알고리즘이다. 문제는 알고리즘이 아니라 **쓰는 방식**이다.
암호화를 실무에서 틀리는 지점은 거의 정해져 있다.

- **IV(초기화 벡터)를 재사용**하거나 예측 가능하게 만든다 → CBC의 안전성이 깨진다.
- 암호화만 하고 **무결성 검증(MAC)을 빠뜨린다** → 공격자가 암호문을 조작해도 알아채지 못한다.
- MAC을 붙여도 **순서를 틀린다**(예: MAC-then-encrypt) → 패딩 오라클류 공격에 노출된다.
- **패딩 처리**에서 실수한다.

하나하나가 그 자체로 깊은 주제다. Fernet은 이 결정들을 **이미 안전한 조합으로 고정해 둔
규격**이다. 남는 선택지는 "키를 만든다 / 암호화한다 / 복호화한다" 정도로 줄어든다. 선택지를
줄이는 것이 곧 실수할 여지를 줄이는 것이다.

---

## 구성 요소

Fernet은 검증된 요소들을 정해진 방식으로 조합한다.

- **AES-128-CBC** — 실제 데이터를 암호화한다(기밀성).
- **HMAC-SHA256** — 토큰 전체에 인증 태그를 붙인다(무결성·인증).
- **타임스탬프 + IV** — 생성 시각을 기록하고(TTL 검증에 사용), 매 암호화마다 새 IV를
  무작위로 생성한다.

핵심은 이것이 단순한 암호화가 아니라 **인증 암호화(authenticated encryption)**라는 점이다.
암호화된 데이터가 한 비트라도 바뀌면 HMAC 검증이 실패하고 복호화 자체가 예외로 끝난다.
조작된 값을 모르고 복호화해 쓰는 사고를 구조적으로 막는다.

```python
from cryptography.fernet import Fernet

# 운영 키가 아니라 데모용으로 그 자리에서 생성한 더미 키다.
key = Fernet.generate_key()          # 32바이트를 URL-safe base64로 인코딩한 형태
f = Fernet(key)

token = f.encrypt(b"db-password-1234")   # 평문 → Fernet 토큰(bytes)
plain = f.decrypt(token)                 # 토큰 → 평문. 변조됐으면 여기서 예외
print(plain)                             # b"db-password-1234"
```

`generate_key()`가 돌려주는 키는 32바이트 랜덤을 URL-safe base64로 인코딩한 문자열이다.
이 32바이트는 내부에서 절반씩 **HMAC용 키(16바이트)**와 **AES 암호화용 키(16바이트)**로
쪼개져 쓰인다. 키 하나로 암호화와 무결성 검증이 동시에 이뤄진다.

## 토큰 구조

Fernet 토큰은 겉보기엔 URL-safe base64 문자열 하나지만, 디코딩하면 정해진 순서로 붙은
바이트 묶음이다.

<!-- 이미지: 구글 검색 "대칭키 암호화 토큰 구조" · 저장 /assets/img/posts/security/fernet/token-structure.png -->

| 필드 | 크기 | 내용 |
|---|---|---|
| Version | 1바이트 | 현재는 `0x80`. 포맷 버전 |
| Timestamp | 8바이트 | 생성 시각(Unix time). TTL 검증에 사용 |
| IV | 16바이트 | 이번 암호화용 초기화 벡터(매번 랜덤) |
| Ciphertext | 가변 | AES-128-CBC로 암호화된 실제 데이터 |
| HMAC | 32바이트 | 앞의 모든 필드에 대한 HMAC-SHA256 태그 |

복호화는 이 구조를 역순으로 밟되, **HMAC부터 검증**한다(version+timestamp+IV+ciphertext
전체 대상). 여기서 어긋나면 즉시 실패하고 AES 복호화까지 가지 않는다. 이 **검증 먼저,
복호화 나중(encrypt-then-MAC)** 순서가 앞의 패딩 오라클류 공격을 막는 핵심이다.

타임스탬프가 토큰 안에 박혀 있으므로, 복호화 시 "며칠 이상 지난 토큰은 받지 않는다"는
만료 정책을 걸 수 있다.

```python
# 발급 후 60초가 지난 토큰은 거부한다
try:
    plain = f.decrypt(token, ttl=60)
except Exception:
    # InvalidToken — 만료됐거나, 변조됐거나, 키가 안 맞거나
    ...
```

주의할 점은 `InvalidToken` 하나가 **여러 실패 원인을 뭉뚱그린다**는 것이다. 만료·변조·키
불일치가 전부 같은 예외로 온다. 토큰만 봐서는 원인을 구분할 수 없으니, 어느 단계에서 났는지
맥락을 함께 로그로 남겨 둬야 디버깅이 편하다.

## 키 로테이션 — MultiFernet

키는 언젠가 바꿔야 한다. 유출 의심이 있거나 주기적 교체 정책이 있을 때다. 문제는 **기존
토큰들이 옛날 키로 암호화돼 있다**는 점이다. 키를 그냥 갈아 끼우면 과거 데이터를 전부
복호화할 수 없게 된다.

`MultiFernet`은 이 무중단 교체를 위해 있다. 여러 키를 리스트로 넘기면,

- **암호화는 항상 맨 앞(첫 번째) 키**로 한다.
- **복호화는 앞에서부터 순서대로** 모든 키를 시도해, 맞는 키를 찾으면 성공한다.

```python
from cryptography.fernet import Fernet, MultiFernet

# 모두 데모용 더미 키
new_key = Fernet.generate_key()
old_key = Fernet.generate_key()

mf = MultiFernet([Fernet(new_key), Fernet(old_key)])

token = mf.encrypt(b"secret")     # 새 키로 암호화
plain = mf.decrypt(token)         # 새 키·옛 키 순서로 시도

rotated = mf.rotate(old_token)    # 옛 키 토큰을 새 키로 재암호화
```

새 키를 맨 앞에 추가해 배포하면 신규 데이터는 새 키로 암호화되고 옛 데이터는 여전히
복호화된다. 이후 `rotate()`로 기존 토큰들을 점진적으로 새 키로 다시 감싼 뒤, 다 끝나면 옛
키를 리스트에서 제거한다. 한 번에 바꾸지 않아도 되는 흐름이다.

## 대칭 vs 비대칭

Fernet은 **대칭키** 방식이다. 암호화하는 키와 복호화하는 키가 같다. RSA 같은 비대칭과의
차이는 다음과 같다.

| 구분 | 대칭키(Fernet 등) | 비대칭키(RSA 등) |
|---|---|---|
| 키 | 암·복호화가 같은 키 하나 | 공개키/개인키 쌍 |
| 속도 | 빠름, 큰 데이터에 적합 | 느림, 작은 데이터용 |
| 쓰임 | 데이터 자체를 저장·암호화 | 키 교환, 서명, 신원 확인 |
| 관건 | **키를 어떻게 안전히 나누고 보관하나** | 개인키 보관 |

한 서버가 저장하고 그 서버가 다시 복호화하는 구조라면 키 쌍이 필요 없다. 키를 주고받을
상대가 없기 때문이다. 이럴 때는 대칭키가 단순하고 빠르다. 비대칭은 서로 모르는 두 주체가
안전하게 키를 나눠 가져야 할 때 쓰는 도구지, 만능 상위호환이 아니다.

## 진짜 어려운 건 키 관리

Fernet을 쓰는 순간 알고리즘 걱정은 라이브러리가 가져간다. 남는 위험은 온전히 **키를
어디에, 어떻게 두느냐**다.

- **소스코드·저장소에 키를 하드코딩하지 않는다.** 리포에 커밋된 키는 이미 유출된 키다.
  환경변수나 시크릿 매니저로 런타임에 주입한다.
- **암호문과 키를 같은 곳에 두지 않는다.** DB에 암호문을 저장하면서 옆에 키까지 두면, DB가
  털리는 순간 암호화의 의미가 통째로 사라진다. 키는 다른 경계에 있어야 한다.
- **키를 하나 더 만드는 것 자체가 부담**이다. 관리할 비밀이 늘수록 실수할 접점도 는다. 이미
  안전하게 관리 중인 강한 비밀(예: 앱의 서명 시크릿)을 SHA-256으로 해시해 32바이트 Fernet
  키로 **파생(derive)**해 쓰면 관리 대상을 늘리지 않는다.
- **교체 가능성을 처음부터 염두**에 둔다. `MultiFernet`이 그래서 필요하다.

이 원칙을 실제 외부 DB 자격증명 저장에 적용한 내용은
[외부 DB 접속 비밀번호 저장](https://rlckdwkd55.github.io/posts/external-db-credentials/)에서
다룬다. 거기서는 [JWT 서명 시크릿](https://rlckdwkd55.github.io/posts/jwt/)에서 키를 파생하는
선택을 했는데, 그 트레이드오프(시크릿을 바꾸면 기존 암호문을 못 푼다)까지 함께 정리했다.

## 인증 암호화가 막는 것

암호화만 하는 방식은 **기밀성**만 준다 — 남이 내용을 읽지 못한다. 하지만 **무결성**은
보장하지 못한다. 공격자가 내용을 읽지 못해도 암호문의 특정 바이트를 조작해 복호화 결과를
바꿔치기할 수 있다.

Fernet은 HMAC을 함께 묶어 이를 막는다. 저장된 토큰이 한 바이트라도 바뀌면 복호화가
`InvalidToken`으로 실패한다. 그래서 **복호화가 성공했다는 것은 이 값이 암호화한 그대로라는
뜻**이 된다. 외부 DB 접속정보처럼 조작되면 엉뚱한 곳에 접속을 시도할 수도 있는 값에서는,
이 무결성 보증이 기밀성만큼 중요하다.

---

정리하면, 복원해 써야 하는 비밀값은 단방향 해시가 아니라 대칭 암호화로 저장한다. Fernet은
AES-128-CBC + HMAC-SHA256 + 타임스탬프를 안전한 순서(encrypt-then-MAC)로 묶어 IV·패딩·MAC을
직접 조립하다 실수할 여지를 없앤 규격이다. 토큰은 `version|timestamp|IV|ciphertext|HMAC`
구조이고 복호화 때 HMAC부터 검증해 변조를 잡아내며 `ttl`로 만료를 건다. 키 교체는
`MultiFernet`으로 무중단 처리한다. 알고리즘은 라이브러리가 책임지므로 남는 위험은 키
관리 — 하드코딩 금지, 암호문과 분리 보관, 파생·교체 고려다.
