Pydantic은 Python의 타입 힌트를 런타임 검증과 직렬화로 바꿔 주는 라이브러리다. 외부에서
들어온 데이터를 `dict` 로 들고 다니면 `email` 키가 없을 때의 `KeyError`, 포트가 문자열일
때의 `TypeError` 가 데이터가 들어온 지점이 아니라 그 데이터를 쓰는 지점에서 뒤늦게 터진다.
Pydantic은 신뢰할 수 없는 입력을 신뢰할 수 있는 타입의 객체로 경계에서 한 번 바꿔 놓는
방식으로 이 문제를 다룬다. 즉, 데이터를 검사만 하고 여전히 `dict` 로 들고 다니는 대신, 한
번 파싱해 유효성을 타입에 남기는 접근이다.

## 타입 힌트는 런타임에 강제되지 않는다

Python의 타입 힌트는 문서와 정적 분석용이다. 다음 코드는 실행 시점에 아무것도 강제하지
않는다.

```python
def create_user(name: str, age: int) -> None:
    ...

create_user(name=123, age="열살")   # 아무 에러도 안 난다
```

`mypy` 같은 정적 분석기로는 잡히지만 런타임에는 통과한다. 그런데 믿을 수 없는 데이터는
대부분 런타임에 들어온다. HTTP 요청 바디, 환경 변수, 외부 API 응답, 메시지 큐가 그렇다. 이
경계에서 선언한 타입이 맞는지 실제로 검사하는 층이 Pydantic이다.

## BaseModel — 검증과 형변환

```python
from pydantic import BaseModel

class User(BaseModel):
    id: int
    name: str
    is_active: bool = True

u = User(id="1", name="kim")   # "1" → 1 로 coercion, is_active 기본값 True
print(u.id, u.is_active)        # 1 True
```

`User(...)` 를 호출하는 순간 각 필드가 선언된 타입에 맞게 검증과 형변환(coercion)을 거친다.
Pydantic v2는 기본적으로 lax(느슨) 모드라 안전하게 변환 가능한 값은 알아서 맞춰 주고,
맞지 않으면 예외를 던진다.

```python
from pydantic import ValidationError

try:
    User(id="abc", name="kim")
except ValidationError as e:
    print(e)
    # 1 validation error for User
    # id
    #   Input should be a valid integer, unable to parse string as an integer ...
```

에러가 어떤 필드가 왜 틀렸는지 구조화되어 나온다. `e.errors()` 로 `loc`(위치)·`type`(에러
종류)·`msg` 를 얻어 API 에러 응답으로 그대로 내려줄 수 있다.

느슨한 변환이 싫으면 `Strict` 타입이나 `model_config` 로 엄격 모드를 켠다.

```python
from pydantic import BaseModel, StrictInt, ConfigDict

class StrictUser(BaseModel):
    model_config = ConfigDict(strict=True)
    id: StrictInt

StrictUser(id="1")   # ValidationError — 문자열을 정수로 강제하지 않는다
```

폼 데이터처럼 값이 모두 문자열로 들어오는 바깥 경계에는 lax가 편하고, 타입이 이미 정확해야
하는 내부 API에는 strict가 안전하다.

## Field — 타입만으로 부족한 제약

타입은 정수인지까지만 말한다. 양수인지, 1~100 사이인지 같은 값 수준 제약은 `Field` 로
건다. v2에서는 `Annotated` 와 함께 쓰는 방식이 권장된다.

```python
from typing import Annotated
from pydantic import BaseModel, Field

class Product(BaseModel):
    name: Annotated[str, Field(min_length=1, max_length=100)]
    price: Annotated[int, Field(gt=0)]                 # 0 초과
    discount: Annotated[float, Field(ge=0, le=1)] = 0  # 0~1
    tags: list[str] = Field(default_factory=list)      # 가변 기본값은 factory로
```

`gt/ge/lt/le`(대소), `min_length/max_length`, `pattern`(정규식) 등이 있다. 리스트·딕셔너리
같은 가변 기본값에는 `default_factory` 를 쓰는 편이 좋다. 다만 흔한 오해 하나를 짚어 두면,
Pydantic에서는 `= []` 로 줘도 **인스턴스마다 기본값을 깊은 복사(deep copy)해 주기 때문에**
모든 인스턴스가 한 리스트를 공유하는 사고는 나지 않는다. 그 함정은 일반 함수 기본 인자나
`dataclass` 쪽 이야기다. 그래도 `default_factory` 를 권하는 이유는 의도가 명시적으로
드러나고, 매 인스턴스마다 새로 만든다는 사실이 코드에 보이기 때문이다.

## 검증자 — field_validator와 model_validator

제약으로 표현되지 않는 규칙은 검증자 함수로 쓴다. v2에는 두 종류가 있다.

`@field_validator` 는 단일 필드를 검증한다. `mode="before"` 는 타입 변환 전(원시 입력을
손질), `mode="after"`(기본)는 변환 후(이미 타입이 맞는 값을 검사)에 돈다.

```python
from pydantic import BaseModel, field_validator

class Signup(BaseModel):
    email: str
    password: str

    @field_validator("email", mode="before")
    @classmethod
    def normalize_email(cls, v: str) -> str:
        return v.strip().lower()          # 저장 전에 정규화

    @field_validator("password")
    @classmethod
    def check_len(cls, v: str) -> str:
        if len(v) < 8:
            raise ValueError("비밀번호는 8자 이상")
        return v
```

`@classmethod` 를 데코레이터 아래에 두는 순서가 v2의 규칙이다. 검증자는 반드시 값을 반환해야
하고, 실패는 `ValueError`(또는 `AssertionError`)로 던지면 Pydantic이 `ValidationError` 로
감싼다.

`@model_validator` 는 여러 필드를 함께 봐야 할 때, 즉 필드 간 관계 검증에 쓴다.

```python
from pydantic import BaseModel, model_validator

class SignupForm(BaseModel):
    password: str
    password_confirm: str

    @model_validator(mode="after")
    def passwords_match(self):
        if self.password != self.password_confirm:
            raise ValueError("비밀번호가 일치하지 않습니다")
        return self       # after 모드는 self를 반환
```

`mode="after"` 는 모델 인스턴스(`self`)를 받고, `mode="before"` 는 원시 입력(보통 dict)을
받는다. 두 필드 중 하나는 반드시 있어야 한다는 식의 교차 규칙은 대개 model_validator다.

## computed_field — 파생 값을 스키마에 포함

저장하지 않고 계산으로 얻는 값을 직렬화 결과에 넣고 싶을 때 쓴다.

```python
from pydantic import BaseModel, computed_field

class Rect(BaseModel):
    width: float
    height: float

    @computed_field
    @property
    def area(self) -> float:
        return self.width * self.height

Rect(width=3, height=4).model_dump()   # {'width': 3.0, 'height': 4.0, 'area': 12.0}
```

일반 `@property` 는 `model_dump()` 에 들어가지 않지만, `@computed_field` 를 붙이면 출력
스키마와 OpenAPI 문서에까지 반영된다.

## 직렬화 — model_dump와 model_validate

경계를 양방향으로 오가려면 파싱(입력)과 직렬화(출력)가 다 필요하다.

```python
u = User.model_validate({"id": 1, "name": "kim"})   # dict → 모델 (검증 포함)
u = User.model_validate_json('{"id": 1, "name": "kim"}')  # JSON 문자열 → 모델

u.model_dump()                # {'id': 1, 'name': 'kim', 'is_active': True}
u.model_dump(exclude={"id"})  # 특정 필드 제외
u.model_dump(mode="json")     # datetime 등을 JSON 호환 타입으로
u.model_dump_json()           # 곧장 JSON 문자열
```

`model_dump(mode="python")`(기본)은 `datetime` 을 그대로 두고, `mode="json"` 은 문자열로
바꾼다. 이 구분을 놓치면 JSON 직렬화가 되지 않는다. `by_alias=True`, `exclude_none=True`
같은 옵션으로 출력 모양을 세밀하게 조절할 수 있다.

## v2가 빠른 이유 — pydantic-core

v2에서 체감되는 가장 큰 변화는 속도다. 검증 로직의 코어(`pydantic-core`)가 Rust로
재작성됐고, Python은 얇은 인터페이스만 담당한다. 모델을 정의하면 각 필드의 검증 계획이 한 번
컴파일되어 재사용되므로, 매 요청마다 Python 레벨에서 타입을 분기하던 v1보다 훨씬 빠르다.
요청량이 많은 API 서버에서는 이 차이가 그대로 처리량으로 이어진다.

## BaseSettings — 설정도 타입 안전하게

환경 변수와 `.env` 를 검증된 객체로 로드한다. v2에서는 별도 패키지 `pydantic-settings` 로
분리됐다.

```python
from pydantic import Field
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", env_prefix="APP_")

    database_url: str                              # 없으면 부팅 시 에러
    debug: bool = False                            # "true"/"1" → True 로 변환
    max_workers: int = Field(default=4, gt=0)

settings = Settings()   # APP_DATABASE_URL, APP_DEBUG ... 를 읽어 검증
```

이점은 잘못된 설정을 부팅 시점에 잡는다는 것이다. `DATABASE_URL` 이 비어 있으면 서버가 뜨는
순간 죽고, 첫 DB 요청이 들어올 때까지 숨어 있지 않는다.

## 어디서 쓰이나 — FastAPI, 그리고 LLM

[FastAPI](https://rlckdwkd55.github.io/posts/fastapi/)는 요청과 응답 스키마를 Pydantic
모델로 선언한다. 요청 바디 검증, 자동 문서(OpenAPI) 생성, 응답 직렬화가 전부 Pydantic 위에서
돈다. 타입을 선언하면 검증·문서·직렬화가 따라온다는 FastAPI의 편의가 사실상 Pydantic의
힘이다. 그 뒤단에서 DB를 비동기로 다루는 내용은
[SQLAlchemy 비동기(AsyncSession)](https://rlckdwkd55.github.io/posts/sqlalchemy-async/)에
따로 정리했다.

또 다른 활용은 LLM 구조화 출력이다. `Model.model_json_schema()` 로 얻은 JSON 스키마를 모델에
넘겨 응답을 그 모양으로 강제하고, 받은 JSON을 `model_validate_json()` 으로 다시 파싱하면 LLM
응답도 신뢰할 수 있는 타입의 객체가 된다. 원리는 같다. 경계에서 한 번 파싱하는 것이다.

## 트레이드오프 — 도메인 모델과의 구분

검증·직렬화용 DTO와 비즈니스 규칙을 담는 도메인 모델은 관심사가 다르다. Pydantic 모델은
경계에서 들어온 모양에 묶이기 쉬워서, 여기에 도메인 로직까지 얹으면 외부 스키마가 바뀔 때
도메인이 함께 흔들린다. 경계 검증은 Pydantic, 내부 규칙은 순수한 도메인 객체로 나누는 편이
안전하다. 이 구분은 [DDD 정리](https://rlckdwkd55.github.io/posts/ddd-domain-driven-design/)에
더 적어 뒀다.

## v1 → v2 이름 변경

버전 문서를 섞어 보면 이름이 꼬인다. 자주 마주치는 변경만 정리한다.

| v1 | v2 |
|---|---|
| `@validator` | `@field_validator` (`@classmethod` 필수) |
| `@root_validator` | `@model_validator` |
| `.dict()` | `.model_dump()` |
| `.json()` | `.model_dump_json()` |
| `Model.parse_obj(d)` | `Model.model_validate(d)` |
| `Model.parse_raw(s)` | `Model.model_validate_json(s)` |
| `class Config:` | `model_config = ConfigDict(...)` |
| `Config.orm_mode = True` | `from_attributes=True` |
| `pydantic.BaseSettings` | `pydantic_settings.BaseSettings` |

`model_` 접두어는 인스턴스 메서드 이름과 사용자 필드가 충돌하지 않도록 붙은 것이다.

Pydantic v2는 경계에서 신뢰할 수 없는 입력을 타입 객체로 한 번 파싱하는 도구다. `BaseModel`
로 스키마를 선언하면 검증·형변환·구조화된 에러가 따라오고, `Field` 와 검증자로 값 제약과
규칙을, `pydantic-settings` 로 부팅 시점 설정 검증을 얻는다. 코어가 Rust라 v1보다 빠르지만
API 이름이 바뀌었으므로 버전을 먼저 확인한다.
