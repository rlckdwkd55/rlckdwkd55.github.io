## 배경: "정상 동작"만 보고 넘어간 코드

기능을 빠르게 붙여 나가다 보니, 어느 순간부터 코드가 **정상 흐름에서만** 검증된 채
쌓이고 있다는 느낌이 들었다. 데모는 잘 돌고 테스트 시나리오도 통과하는데, 정작
**실패했을 때·악의적인 입력이 들어왔을 때·경계 조건에 닿았을 때** 어떻게 되는지는
아무도 확인한 적이 없는 지점들이었다.

한 번은 청크 하나를 수정하다가 임베딩 서버가 잠깐 죽어 있으면 원본 청크가 통째로
사라진다는 걸 우연히 발견했고, 그때 "이런 게 여기 하나뿐일 리 없다"는 생각이 들었다.
그래서 새 기능을 붙이는 대신, 하루를 잡고 **보안·정합성·예외 처리 세 가지 렌즈로
기존 코드를 전수로 훑는 점검**을 진행했다. 그 결과가 커밋 하나
(`fix: 보안/정합성 결함 수정 및 예외처리 전수 보강, RBAC Execute 권한 추가`,
33개 파일 변경)로 정리됐고, 이 글은 그때 무엇을 어떤 관점으로 걷어냈는지에 대한
회고다.

## 어떤 관점으로 훑었나

혼자 코드를 처음부터 다시 읽으면서, 파일마다 세 가지 질문을 반복해서 던졌다.

- **보안** — 이 값은 사용자가 조작할 수 있는가? 조작된 값이 파일 시스템·권한·외부
  연결에 그대로 흘러 들어가는가?
- **정합성** — 이 연산이 도중에 실패하면 데이터가 어떤 상태로 남는가? 되돌릴 수
  있는가?
- **예외 처리** — 이 `try`가 잡는 범위가 실제 실패와 맞는가? 실패가 전체 흐름을
  죽이거나, 반대로 조용히 삼켜지지는 않는가?

이 세 질문을 기준으로 잡은 대표 사례를 아래에 정리한다. 각각은 별도 글에서 더 깊게
다루고, 여기서는 "무엇이 문제였고 어떻게 바꿨는가"의 요지만 남긴다.

## 대표 결함 ① 되돌릴 수 없는 순서 — 재임베딩 "삭제 후 재생성"

이번 점검을 시작하게 만든 결함이다. 청크 하나를 수정하면 그 내용을 다시 임베딩해서
벡터 DB에 반영하는데, 기존 코드는 순서가 이랬다.

1. 기존 포인트를 **먼저 삭제**한다
2. 수정된 내용을 재임베딩해서 **새 포인트로 저장**한다

정상 흐름에서는 아무 문제가 없다. 하지만 1번이 성공한 직후 2번(임베딩 모델 호출·저장)
에서 예외가 나면, **원본 청크는 이미 사라졌고 새 청크는 만들어지지 못한** 상태로
남는다. 즉 되돌릴 수 없는 순서였다. 임베딩은 외부 모델 서버·GPU에 의존하는, 언제든
실패할 수 있는 연산이라 더 위험했다.

수정은 순서를 뒤집는 것이었다. **재생성이 성공한 것을 확인한 뒤에 기존 것을 삭제**하는
build-then-swap으로 바꿨다.

```python
# before: 삭제가 먼저 → 재임베딩 실패 시 원본 유실
# after: 새 포인트 저장 성공 → 그 다음 기존 포인트 삭제
new_doc = Document(page_content=new_content, metadata=metadata)
await self.add_documents(collection_name, [new_doc])   # 먼저 만든다
await self.client.delete(collection_name=collection_name, ...)  # 성공 후 지운다
```

"파괴적 연산은 대체재가 준비된 뒤에"라는 원칙은 배포(blue-green)나 인덱스 재구성에서
익숙했는데, 정작 내 데이터 연산에는 적용하지 못하고 있었다.
→ [자세히](https://rlckdwkd55.github.io/posts/reembedding-order/)

## 대표 결함 ② 신뢰할 수 없는 입력 — 파일명이 곧 저장 경로

파일 업로드 로직은 사용자가 보낸 파일명을 **그대로 저장 경로에 이어 붙이고** 있었다.
파일명에 상위 디렉터리를 가리키는 경로 구성요소가 섞여 들어오면, 저장 위치가 업로드
루트를 벗어날 수 있는 전형적인 path traversal 구조였다. 정상적인 파일명만 들어온다는
가정 하나에 파일 시스템 전체가 노출돼 있던 셈이다.

방어는 두 겹으로 넣었다. 첫째, 파일명에서 **디렉터리 구성요소를 제거하고 순수 파일명만**
취한다. 둘째, 최종 저장 경로를 실제로 계산한 뒤 **그 경로가 업로드 루트 안에 있는지
사전 검증**하고, 벗어나면 거부한다.

```python
filename = LibPath(upload_file.filename).name   # 경로 성분 제거, 파일명만
if not filename:
    raise CommonException(ErrorCode.FILE_UPLOAD_ERROR)
...
if not upload_path.resolve().is_relative_to(upload_dir.resolve()):
    raise CommonException(ErrorCode.FILE_UPLOAD_ERROR)  # 루트 이탈 봉쇄
```

핵심 교훈은 "정규화든 검증이든 하나만 믿지 말자"였다. 파일명 정규화라는 방어 하나로
끝내지 않고, **정규화가 뚫렸을 때를 대비한 경로 봉쇄**를 한 겹 더 둔 게 이 수정의
요점이다. → [자세히](https://rlckdwkd55.github.io/posts/path-traversal-file-upload/)

## 대표 결함 ③ 검증 없던 API — RBAC에 실행(Execute) 권한 추가

권한 관점으로 라우터를 훑다가, **권한 검증이 아예 걸려 있지 않은 API 몇 개**를
발견했다. 외부 DB 연결 테스트, 스케줄러 즉시 실행, 문서 재동기화였다. 셋 다 조회·수정과
성격이 달랐다. 리소스를 읽거나 바꾸는 게 아니라 **부수 효과가 있는 동작을 실행**하는
API인데, 기존 RBAC은 CRUD 4단계밖에 없어서 이들을 어디에 끼워 넣어야 할지 애매했고
그래서 방치돼 있었던 것이다.

그래서 권한 모델에 **실행(Execute)을 정식 단계로 추가**했다. 엔티티에 `can_execute`
컬럼을 더하고(기존 데이터 호환을 위해 `server_default='0'`), 권한 검사 디스패치에
`execute`를 등록한 뒤, 방치돼 있던 3개 API의 게이트를 `update`가 아니라 `execute`로
바꿔 걸었다.

```python
# require_can: 검사 대상에 execute 추가
{
    "read": perm.can_read, "create": perm.can_create,
    "update": perm.can_update, "delete": perm.can_delete,
    "execute": perm.can_execute,      # 추가
}.get(operation, False)

# 방치돼 있던 3개 API에 게이트 부착 (update → execute)
@router.post("/test-connection", dependencies=[Depends(require_can(MenuType.EXTERNAL_DB, "execute"))])
@router.post("/jobs/{seq}/trigger", dependencies=[Depends(require_can(MenuType.SCHEDULER, "execute"))])
@router.post("/{seq}/refresh-external-db", dependencies=[Depends(require_can(MenuType.DOCUMENTS, "execute"))])
```

"실행"을 억지로 update에 욱여넣지 않고 권한 모델 자체를 확장한 게 맞는 판단이었다고
본다. 부수 효과가 있는 동작은 CRUD와 다른 위험을 가지므로, 권한도 따로 관리돼야
했다. 권한 DTO에는 `menu_type` 중복 방지 검증도 함께 넣어, 같은 메뉴에 상충하는 권한이
저장되는 것을 원천 차단했다. → [자세히](https://rlckdwkd55.github.io/posts/rbac-permission-gate/)

## 함께 걷어낸 것들

대표 3건 외에도, 같은 세 렌즈로 훑으며 잔결함을 여러 개 정리했다.

- **가짜 안전장치 — 빈 비밀번호 연결 테스트.** 외부 DB 수정 화면에서 비밀번호를
  비운 채 연결 테스트를 하면 빈 값으로 요청이 나가 **매번 실패**하고 있었다. 사용자
  입장에선 "저장된 접속 정보로 테스트되겠지" 싶은 동작이 실제로는 아무것도 검증하지
  못하는 상태. 비밀번호가 비어 있으면 **기존 저장값으로 폴백**하도록 고쳤다.
  → [자세히](https://rlckdwkd55.github.io/posts/external-db-credentials/)
- **예외 범위 좁히기.** 광범위하게 잡던 `except`를 예상 가능한 예외로 좁히고, 실패해도
  전체 흐름이 죽지 않도록 격리했다. 예컨대 시나리오 저장 시 Qdrant 동기화 실패는
  삼키지 않고 `VECTOR_SYNC_FAILED`로 명확히 올리도록, 임베딩 모델 다운로드 실패는
  원인과 대처법을 로그로 남긴 뒤 재던지도록 바꿨다.
- **정합성 잔버그 두 개.** 문서를 삭제할 때 로컬 파일만 지우고 **벡터 DB 포인트는
  남던** 문제, 그리고 SQLAlchemy 관계에서 `back_populates`가 이미 등록한 엔티티를
  코드가 한 번 더 `append`해 **중복 INSERT**가 나던 문제를 잡았다.
- **환경 의존 제거.** `ROOT_PATH`가 특정 개발 PC 경로로 하드코딩돼 있던 것을,
  **파일 위치 기준으로 자동 도출**하도록 바꿔 환경마다 손대지 않아도 되게 했다.
- **중복 로직 통합.** `point_id`(UUID/int) 파싱이 두 곳에 각각 구현돼 있어, 공용
  유틸(`app/utils/point_id.py`)로 합치고 예외 처리도 일관되게 맞췄다.

## 혼자 전수로 훑으며 배운 것

가장 크게 남은 건 **결함이 몰려 있는 위치가 일정하다**는 감각이다. 이번에 잡은
것들은 하나같이 정상 흐름 바깥, 즉 실패 경로·경계·조작된 입력에 숨어 있었다. 기능을
만들 때는 "되게 하는" 데 집중하느라 이쪽을 잘 안 보게 되는데, 나중에 렌즈를 바꿔
한 번에 훑으면 비슷한 결함이 무더기로 드러났다. 개별로는 사소해 보여도, 같은 종류의
실수가 코드베이스 전반에 반복돼 있었다는 게 진짜 문제였다.

재발을 줄이기 위해 스스로 정한 것도 있다. 앞으로 **파괴적 연산을 짤 때는 "중간에
실패하면 데이터가 어떤 상태로 남는가"를 먼저 적고 시작**하기로 했다. 그리고 부수
효과가 있는 동작을 새로 추가하면, 만들자마자 권한 게이트를 함께 다는 것을 기본
절차로 삼았다. 기능과 별개로 이런 전수 점검 시간을 주기적으로 확보하는 게, 결국
배포 뒤에 터질 사고를 앞당겨 처리하는 가장 싼 방법이라는 걸 이번에 체감했다.

## 정리

- 보안·정합성 결함은 대개 정상 흐름이 아니라 **실패 경로·경계·조작된 입력**에 숨는다
- 파괴적 연산은 **대체재를 먼저 만든 뒤 지우는(build-then-swap)** 순서로 짜야
  중간 실패에 데이터가 안전하다
- 신뢰할 수 없는 입력은 **정규화 하나에 기대지 말고 봉쇄 검증을 한 겹 더** 둔다
- 부수 효과가 있는 동작은 CRUD와 다른 위험을 가지므로 **권한 모델도 따로**
  관리한다(Execute)
- 같은 렌즈로 코드를 전수로 훑으면, 흩어져 있던 동종 결함을 배포 전에 한 번에 걷어낼
  수 있다
