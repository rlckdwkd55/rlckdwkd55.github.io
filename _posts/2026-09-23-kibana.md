Kibana는 Elasticsearch에 쌓인 데이터를 검색·탐색하고, 집계 결과를 차트와 대시보드로
그려 주는 웹 UI다. 데이터를 **쌓는 일**과 그것을 사람이 이해할 수 있게 **보여 주는 일**은
별개의 문제다. [ELK 스택](https://rlckdwkd55.github.io/posts/elk-stack/)에서 Logstash가
데이터를 가공해 넣고 Elasticsearch가 저장·검색을 맡는다면, Kibana는 그 결과를 꺼내
보여 주는 마지막 조각이다. 동작은 데이터 뷰 → 탐색 → 집계 → 시각화 순으로 이어진다.

---

## 데이터 뷰(Data View)를 먼저 만드는 이유

Kibana에서 Discover를 열거나 차트를 그리려 하면 "데이터 뷰를 먼저 만들라"는 안내가
나온다. Elasticsearch에는 인덱스가 수십·수백 개 있을 수 있고, 실무에서는 보통 날짜별로
롤오버된 인덱스(`app-logs-2025.12.10`, `app-logs-2025.12.11` …)가 쌓인다. Kibana가
"무엇을 보여줄지" 알려면 이 인덱스들을 **하나의 논리적 대상으로 묶는 이름**이 필요하다.
그것이 데이터 뷰다(구버전 용어로는 index pattern).

```text
app-logs-*
```

와일드카드로 지정하면 날짜별 인덱스 전체가 한 데이터 뷰로 묶인다. 데이터 뷰를 만들 때
Kibana가 하는 또 하나의 중요한 일은 **필드 목록과 타입을 파악**하는 것이다. 어떤 필드가
`keyword`이고 어떤 필드가 `text`인지, 숫자인지 날짜인지를 ES 매핑에서 읽어 온다. 이
정보가 있어야 "이 필드로 집계할 수 있는가"를 판단할 수 있다.

시계열 데이터라면 생성 시 **시간 필드**(`@timestamp` 등)를 지정한다. 이걸 지정하는 순간
화면 우상단의 시간 필터가 살아나고, "최근 15분", "지난 24시간" 같은 기간 필터가 모든
화면에 걸린다. 시간 필드를 잡지 않으면 시계열 차트를 그릴 수 없다.

> 데이터 뷰는 물리적으로 데이터를 복사하거나 옮기지 않는다. "어떤 인덱스를 어떤 필드
> 구성으로 볼지"를 정의한 메타데이터일 뿐이다. 그래서 데이터 뷰를 만들거나 지워도 원본
> 인덱스는 그대로다.

## Discover와 KQL

데이터 뷰를 만들었으면 **Discover**에서 실제 문서를 들여다본다. 장애 대응의 출발점이
되는 화면이다. 기간을 좁히고, 왼쪽 필드 목록에서 관심 필드에 필터를 걸고, 검색어로
범위를 줄여 가며 지금 무슨 일이 벌어지는지를 확인한다.

검색에는 **KQL(Kibana Query Language)** 을 쓴다. Lucene 문법보다 읽기 쉽고 필드
자동완성이 잘 된다.

```text
level: "ERROR" and service: "payment-api"
```

```text
status_code >= 500 and response_time_ms > 1000
```

두 번째 쿼리처럼 숫자 비교(`>=`, `>`)도 가능한데, 이게 되려면 `status_code`나
`response_time_ms`가 매핑에서 숫자 타입이어야 한다. 문자열(`text`)로 색인돼 있으면 비교
연산이 먹지 않는다. 여기서도 "화면이 이상하면 원인은 색인 단계"라는 원칙이 그대로
적용된다.

와일드카드와 존재 여부 검사도 자주 쓴다.

```text
url_path: /api/search/* and not user_id: *
```

이건 "검색 API로 들어온 요청 중 `user_id` 필드가 아예 없는(비로그인) 트래픽"을 뽑는
방식이다. `not 필드: *`는 "해당 필드가 존재하지 않는 문서"를 의미한다. Discover에서
조건을 좁혀 원인 문서를 찾은 뒤 그 조건을 그대로 시각화로 넘기면, 조사에서 대시보드화로
자연스럽게 이어진다.

## 집계(Aggregation) — 시각화의 근간

Kibana의 거의 모든 시각화는 결국 ES의 **집계(aggregation)** 결과를 그림으로 옮긴 것이다.
차트를 이해하려면 집계를 먼저 이해해야 한다. 집계는 크게 두 종류로 나눠 보면 정리가 된다.

- **버킷(bucket) 집계** — 문서를 그룹으로 나눈다. "필드 값별로", "시간 구간별로", "숫자
  범위별로" 문서를 묶는다. 차트의 **X축(가로 분류)** 에 해당한다.
- **메트릭(metric) 집계** — 각 그룹 안에서 숫자를 계산한다. 개수(count), 합계, 평균,
  최댓값, 고유값 개수(cardinality) 등. 차트의 **Y축(높이·크기)** 에 해당한다.

"시간대별 요청 수" 차트는 `@timestamp`를 일정 간격으로 나누는 **date histogram 버킷** +
각 구간의 **count 메트릭**이다. "서비스별 평균 응답시간"이라면 `service` 필드로 나누는
**terms 버킷** + `response_time_ms`의 **avg 메트릭**이 된다.

인기 검색어 Top 10 같은 차트도 마찬가지다. "가공된 검색어 필드(`search_keyword`, keyword
타입)로 terms 집계 → 상위 10개, 각 버킷의 count"라는 질의가 곧 막대그래프가 된다. 여기서
`search_keyword`는 반드시 `keyword` 타입이어야 한다. `text` 타입은 분석기가 토큰을 쪼개
버려 terms 집계에 부적합하고, `keyword`여야 "노트북 거치대"가 통째로 하나의 버킷이 된다.
[역색인 구조](https://rlckdwkd55.github.io/posts/elasticsearch-inverted-index/)에서 정리한
`text`와 `keyword`의 색인 방식 차이가 시각화 단계에서 이렇게 드러난다.

## Lens와 시각화

**Lens**는 요즘 Kibana에서 시각화를 만들 때 가장 먼저 권장되는 도구다. 필드를 드래그해
X축·Y축에 놓으면 Kibana가 적절한 집계를 골라 준다. 앞의 버킷/메트릭 개념을 알면 Lens가
뒤에서 어떤 집계를 만드는지가 보인다.

| 알고 싶은 것 | 버킷(X축) | 메트릭(Y축) | 차트 |
| --- | --- | --- | --- |
| 시간대별 트래픽 추이 | `@timestamp` date histogram | count | 선/막대 |
| 상위 검색어 Top 10 | `search_keyword` terms | count | 가로 막대 |
| 서비스별 평균 응답시간 | `service` terms | avg(`response_time_ms`) | 막대 |
| 에러 레벨 비율 | `level` terms | count | 파이 |
| 순 방문자 수 | (없음) | cardinality(`user_id`) | 단일 숫자 |

마지막 행처럼 버킷 없이 메트릭만 쓰면 "전체 기간의 고유 사용자 수" 같은 단일 지표
패널이 된다. cardinality는 고유값 개수를 세는 집계인데, 대용량에서는 근사치를 반환한다.
숫자가 미묘하게 어긋날 때 당황하지 않으려면 알아 둘 특성이다.

## 대시보드

개별 차트를 만들었으면 **Dashboard**에 모은다. 대시보드는 여러 시각화 패널을 한 화면에
배치한 조합 보드다. 트래픽 추이, 에러 비율, 상위 검색어, 평균 응답시간을 한 페이지에
올려 두면 서비스 상태를 한눈에 관찰할 수 있다.

대시보드의 핵심은 **필터가 전역으로 걸린다**는 점이다. 상단에서 기간을 "지난 1시간"으로
바꾸면 모든 패널이 동시에 그 기간으로 다시 그려진다. KQL 검색창에 `service: "payment-api"`를
입력하면 대시보드 전체가 결제 서비스 기준으로 필터링된다. 하나의 조건으로 여러 관점을
동시에 좁혀 보는 이 방식이 장애 조사에서 큰 차이를 만든다.

## 운영: Alerting과 Dev Tools

**Alerting** — 대시보드를 계속 지켜볼 수는 없으므로 조건을 걸어 두고 자동으로 알림을
받는다. "최근 5분간 `level: ERROR` 문서가 100건을 넘으면 Slack으로 통지" 같은 규칙을
만들 수 있다. 이것도 결국 "일정 주기로 집계를 돌려 임계값과 비교"하는 구조라, 앞의 집계
개념이 그대로 이어진다.

**Dev Tools 콘솔** — Kibana 안에는 ES REST API를 직접 실행하는 콘솔이 들어 있다. 매핑을
확인하거나(`GET app-logs-*/_mapping`) 집계 쿼리를 날것 그대로 실험할 때 요긴하다.

```text
GET app-logs-*/_search
{
  "size": 0,
  "aggs": {
    "top_keywords": {
      "terms": { "field": "search_keyword", "size": 10 }
    }
  }
}
```

이 집계를 직접 실행해 보면 Lens가 인기 검색어 차트 뒤에서 어떤 요청을 보내는지가 그대로
드러난다. 시각화와 집계가 결국 같은 것임을 확인하는 지점이다.

> Kibana는 어디까지나 **보는 도구**다. 차트가 이상하면 원인은 대개 Kibana가 아니라 색인
> 단계에 있다. 필드 타입이 잘못됐거나([Logstash](https://rlckdwkd55.github.io/posts/logstash/)
> 가공·매핑 문제), 데이터가 애초에 들어오지 않았거나. Kibana를 붙잡기 전에 데이터 뷰의
> 필드 타입과 원본 문서부터 확인하는 편이 빠르다.

---

정리하면 Kibana는 ES 데이터를 검색(Discover)·시각화(Lens)·대시보드로 보여 주는 뷰
계층이다. 데이터 뷰를 먼저 만드는 이유는 흩어진 인덱스를 하나로 묶고 필드 타입과 시간
필드를 파악하기 위해서다. Discover에서 KQL로 원본을 좁히고, 그 조건을 그대로 시각화로
넘긴다. 모든 시각화의 근간은 집계이며, 버킷(X축 분류)과 메트릭(Y축 계산)으로 차트를
읽으면 Lens가 쉬워진다. terms 집계에는 `keyword` 타입이 필요하듯, 데이터 품질은 결국
색인·매핑 단계에서 결정된다.
